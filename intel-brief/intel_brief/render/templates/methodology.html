Methodology

How each edition is made

What is automated, what a model writes, what code decides, and what a person checks before anything is published.

1. Collection (code)

Every morning a script reads free public sources: the CISA Known Exploited Vulnerabilities catalog, NVD (recent high and critical CVEs), FIRST EPSS scores, Microsoft and CISA advisories, security news feeds, new SigmaHQ rules, an index of public proof-of-concept repositories, and posts that mention CVEs on Bluesky, Mastodon (infosec.exchange), r/netsec and Hacker News. X/Twitter is not used.

Each edition covers one day: the whole of the day before its own date, US Eastern, and nothing outside it. So the edition dated 6 November reports 5 November. That is a deliberate day's delay. A first report is often wrong about who was hit, which versions are affected or whether a fix exists, and a day is usually enough for the correction, the vendor advisory or the retraction to arrive. The cost is that nothing here is breaking news; if you need the first word on something, this is the wrong page. The window is fixed by the edition's date rather than by when the job runs, so a late run publishes the same edition, only later.

2. Ranking (model labels, code scores)

Claude Haiku groups items about the same event into stories and labels each one: exploitation status, how widely the product is deployed, and which platform it hits. The priority score is then computed by code from those labels plus facts the collector already has: KEV status, EPSS, CVSS and how many outlets reported it. CVE IDs on the page always come from the collected items, never from the model.

3. Summaries (model)

For the top stories, Claude Opus (or Sonnet) writes what happened, why it matters, affected and fixed versions, and what to do, using only the collected items. It cannot browse, run tools or add links: every link on the page was gathered by the collector and checked against an allowlist. Summaries can still be wrong or incomplete. Each one shows how well its sources supported it. If the model declines a request, Anthropic's API can pass it to an earlier Claude model instead; the label under each piece names the model that actually wrote it.

4. Detections (model and code)

If SigmaHQ already has a rule for a CVE, that rule is used and converted automatically. Otherwise the model drafts a Sigma rule, which code assembles and checks with sigma check; rules that fail are dropped. Rules are converted with pySigma to Defender XDR KQL, Splunk SPL and Elastic, and every KQL query is parsed with Microsoft's Kusto.Language against the Defender XDR and Sentinel schemas. Hunting queries that contain an indicator not found in the sources are dropped.

Every KQL query then runs on Microsoft's Kusto emulator. A Sigma rule's KQL conversion runs on labelled cases built from the rule: each selection met, each alternative value tried, each filter applied, letter case changed, and each field broken in turn. An independent Sigma evaluator, which shares no code with pySigma, decides which cases should match, so a conversion that misses or over-matches shows up. Every query also runs on a small synthetic baseline of ordinary activity, and the page shows how many rows it returned there. None of this is a test on real attack data. A rule whose conversion passes its cases is labelled "KQL tested", meaning tested on those synthetic cases only; everything else AI-generated stays "AI-generated, untested". Test and tune before you deploy anything.

5. Early signals (code)

A CVE becomes an early signal when several independent accounts post about it within the window and it is not yet in KEV or the news feeds. Accounts that post about many CVEs a day are treated as feed bots and posts naming many CVEs as digests; neither counts. No model is involved.

6. Explainer and good news (model)

After the summaries, one more call to the same model writes two short sections. The Explainer takes one concept behind the day's stories, such as an attack technique, a protocol weakness or a defensive control, and explains it in a couple of paragraphs to a few headed parts, depending on how involved it is. It is written from the model's background knowledge, not from the day's sources, so it is labelled that way, and any CVE it names that no source mentions is flagged. Good news picks up to four positive developments from the collected news, such as takedowns, arrests, fixes shipped and new defenses. Each one links only to the collected articles it summarizes.

7. Review and publishing (a person)

Each edition is proposed as a pull request. Nothing is published until a person reviews and merges it. The site publishes summaries and links only, never copies of articles. Proof-of-concept repositories are listed as links, unvetted, with a warning.
