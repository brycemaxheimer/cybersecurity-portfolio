What happened

Rapid7 reports that on 29 October 2026 Ivanti updated its Connect Secure advisory with two more vulnerabilities and released fixes: CVE-2026-111357, a local authenticated privilege escalation, and CVE-2026-118527, which CISA's KEV entry describes as letting a remote authenticated attacker upload attacker-controlled content to a known path on disk. Ivanti says a limited number of customers were exploited before disclosure, with both flaws chained to the previously disclosed authentication bypass CVE-2026-104935, and fixes now exist for all three. Volexity attributes the activity to UTA0576, which gained unauthenticated root access to an appliance running 22.8R2.4 from 3 October 2026 and then stole credentials and queried Active Directory for Windows LAPS passwords and BitLocker recovery keys. CISA added both new CVEs to KEV on 30 October 2026.

Why it matters

All three CVEs are in CISA KEV and exploitation is confirmed. CVE-2026-104935 has public exploit code and an EPSS of 88.9%, so internet-facing Connect Secure appliances that are not fully patched should be treated as at risk of root compromise. The sources disagree on CVE-2026-111357 severity: Ivanti scores it 8.8 while the CVE record scores it 7.0. Because the attacker pivoted into Active Directory for LAPS and BitLocker secrets, a compromised appliance also puts Windows endpoints and domain credentials at risk.

What to do

  1. Apply Ivanti's fixes for all three CVEs to every Connect Secure appliance immediately, as the vendor advisory directs.
  2. Run Ivanti's integrity checking and review appliance logs for signs of compromise since early October 2026; if compromise is suspected, follow Ivanti's rebuild guidance.
  3. Rotate credentials that transit or are stored on the appliance, including the AD service accounts it uses, and VPN user passwords where compromise is suspected.
  4. If the appliance may have been compromised, rotate Windows LAPS passwords and BitLocker recovery keys that its accounts could read.
  5. Hunt for Active Directory reads of LAPS and BitLocker attributes and for unusual LDAP or logon activity originating from the appliance's internal IP.

Microsoft: fake-download installers silently turn PCs into proxyware and compute-sharing nodes

1 source · first reported 3 November 2026

What happened

Microsoft Threat Intelligence reported on 3 November 2026 a fake-download campaign aimed at users looking for cracked software, free games, activators, plugins and unofficial utilities. According to Microsoft, trojanized Inno Setup-style installers deliver several monetized payloads, which the delivery system calls offers, in one installation session and report each offer's outcome back through a callback and status-tracking model. Microsoft confirmed three monetization branches: routing third-party internet traffic through the device, enrolling it in a distributed-computing platform, and installing extra utility-style software, often without informed user consent. The installer stages a temporary runner under %TEMP%\is-*.tmp\ that launches numbered stages such as eld*.exe or set_*.exe, which contact rotating infrastructure using a repeatable d=inno and r=offer_execution callback pattern. The available Microsoft text is truncated, so the specific payload names and indicators are not available here.

Why it matters

Microsoft describes the activity as evolving and active. Any corporate Windows device whose user downloads pirated or unofficial tools can end up relaying unknown third-party traffic from your egress IPs, burning compute, and carrying persistent unwanted software. Proxyware traffic from corporate addresses can lead to abuse reports and reputation damage. It can also hide malicious traffic. The bundles may look legitimate individually, so standard malware verdicts can miss them unless potentially unwanted application (PUA) protection is enabled.

What to do

  1. Enable PUA protection in block mode in Microsoft Defender Antivirus and Defender for Endpoint across all Windows devices.
  2. Hunt for Inno Setup temporary runners under %TEMP%\is-*.tmp\ that spawn eld*.exe or set_*.exe stages. Isolate and reimage hosts where proxyware or distributed-computing clients were installed.
  3. Block untrusted software sources: restrict user installs with application control such as WDAC, AppLocker or Intune, and limit local admin rights.
  4. Review endpoints for unexpected new software, services, scheduled tasks and Run-key persistence created after installer execution.
  5. Watch egress for sustained unexplained relay traffic from workstations that could indicate bandwidth-sharing software, and block known proxyware services at the proxy.

What happened

CISA added CVE-2026-119977, a time-of-check time-of-use race condition in WordPress core, to its Known Exploited Vulnerabilities catalog on 3 November 2026. According to CISA, unauthenticated attackers can run code on the server during the upgrade window because full-package core upgrades use predictable, web-accessible staging paths. BleepingComputer reports that attackers are exploiting the recently patched flaw in the wild. The sources do not name affected or fixed version numbers.

Why it matters

Any internet-facing WordPress site, including ones on Windows/IIS servers, can be compromised without credentials while a core upgrade runs. That turns routine patching into the attack window. The flaw is confirmed exploited, public proof-of-concept code exists, CVSS is 8.1 and EPSS is 1.0%, and CISA set a KEV due date of 6 November 2026, so treat this as urgent.

What to do

  1. Inventory all WordPress installations, including shadow and marketing sites, and apply the vendor's patched core release and mitigation guidance before the 6 November 2026 KEV due date.
  2. Until patched, block web access to the core upgrade staging directory (wp-content/upgrade) at the web server or WAF so files placed there cannot be requested.
  3. Review web server logs and file telemetry for PHP files created or requested under wp-content/upgrade, especially around recent core upgrade times.
  4. Hunt for web server or PHP processes spawning shells or recon tools on WordPress hosts, and investigate any hits as possible compromise.
  5. On suspected compromise, follow CISA forensics triage guidance: preserve logs, check for web shells and new admin accounts, and rotate database and WordPress secrets.

Operation CloudFire phishing used Google Calendar invites to hijack corporate Google sessions

Google Google Calendar · 1 source · first reported 4 November 2026

What happened

BleepingComputer reports on a phishing campaign, tracked by Material Security as Operation CloudFire, that sent Google Calendar invitations to corporate users. The invitations led victims through trusted redirects to fake login pages built to steal authenticated sessions and get around MFA. According to the report, Material Security blocked the malicious messages and helped take down nearly 900 attacker domains. The available reporting does not name affected organizations, indicators, or the exact session-theft technique.

Why it matters

Calendar invites from Google infrastructure often pass email authentication checks and can add events to calendars without a click, so they bypass the usual filtering that phishing awareness relies on. Session hijacking defeats MFA that is not phishing-resistant. The same adversary-in-the-middle approach carries over to Microsoft 365 and Entra ID, so organizations using Google Workspace, or users who reach SaaS through Google identities, should treat stolen sessions as an active risk.

What to do

  1. In Google Workspace, configure Calendar so invitations from external or unknown senders are not added to calendars automatically.
  2. Revoke active sessions and reset credentials for any user who interacted with an unexpected external calendar invite that led to a login page.
  3. Move privileged and high-risk users to phishing-resistant MFA such as FIDO2 security keys or passkeys, in both Google Workspace and Entra ID.
  4. Hunt inbound mail for Google Calendar invitations from unknown external organizers that contain links to non-Google login pages.
  5. Remind users that a calendar invite asking them to sign in is a phishing indicator, and give them a quick way to report it.

Explainer

Background, not news

Chaining low-privilege bugs into unauthenticated root on edge appliances

Attackers combine an authentication bypass with privilege escalation or file-write flaws to turn limited access into full control of a VPN, firewall, or email gateway.

Why today. The Ivanti Connect Secure and Barracuda ESG advisories both describe exploit chains where an auth bypass is paired with a second flaw to reach root, showing why individual CVSS scores understate the real risk. See story 1.

Why one bug is rarely enough

Internet-facing appliances expose a thin pre-authentication surface and a much larger set of functions available after login. A single authentication bypass often lands an attacker in a limited, authenticated context rather than giving immediate control. Likewise, a privilege escalation or arbitrary file-write bug is only reachable once you are already on the box.

Treated in isolation, each of these flaws may carry a modest CVSS score and look like a lower priority. Chained together, they let an attacker move from no credentials to root in a single operation. This is why a 'medium' file-upload or privilege-escalation CVE can be the critical link that makes an exploit chain work.

What the chain looks like in practice

In the Ivanti case, an authentication bypass is combined with a flaw that lets a remote authenticated attacker write attacker-controlled content to a known path on disk, plus a local privilege escalation. The bypass grants authenticated access, the file-write plants code at a predictable location, and the escalation finishes the job at root. Volexity reports the actor then stole credentials and queried Active Directory for LAPS passwords and BitLocker recovery keys.

The Barracuda ESG advisory follows the same pattern: an authentication bypass chained with a command injection flaw yields root on the appliance. The structure is consistent across vendors because the appliance architecture is similar.

What it means for detection

Post-exploitation on these devices looks like unexpected files appearing in web-accessible or staging paths, new processes spawned by the web server, and outbound connections from an appliance that normally only receives them. Because the appliance is often the pivot point, the loudest signal may appear downstream: an appliance service account suddenly authenticating to domain controllers or querying directory attributes it never touched before.

After the Ivanti activity, defenders should treat directory queries for LAPS passwords and BitLocker recovery keys originating from or shortly after appliance compromise as high-fidelity indicators, and assume credentials handled by the device are exposed.

For defenders

  1. Apply the Ivanti Connect Secure fixes for CVE-2026-104935, CVE-2026-111357, and CVE-2026-118527 immediately; both new CVEs are in CISA KEV as of 30 October 2026.
  2. Do not deprioritize medium-severity auth-bypass, file-write, or privilege-escalation CVEs on edge devices; they are the chain links that turn into root.
  3. Patch Barracuda ESG for the auth-bypass and command-injection chain that leads to root.
  4. Hunt for LAPS password and BitLocker recovery key queries in Active Directory and treat appliance-sourced directory reads as suspicious.
  5. Assume credentials, certificates, and secrets stored on any exploited appliance are compromised and rotate them after patching.
