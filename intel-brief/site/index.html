Huntress: Teams meeting-booking lure used to hide device code phishing

Microsoft Teams · 1 source · first reported 12 November 2026

What happened

Huntress reports that threat actors built a convincing Microsoft Teams meeting-booking flow to disguise device code phishing. The lure leads victims to complete a legitimate Microsoft device code sign-in, which authorizes the attacker's session and gives them access to the victim's account. The sources do not name the actor, the targeted sectors, the scale of the campaign or any indicators.

Why it matters

Device code phishing uses Microsoft's real sign-in pages, so URL reputation checks and user awareness of fake login pages often miss it. When it succeeds, the attacker receives tokens for the victim's Entra ID account, and MFA does not stop that. Huntress describes this as active use against victims. Any tenant that still allows the device code flow for ordinary users is exposed.

What to do

  1. Block the device code authentication flow with a Conditional Access authentication flows policy, and allow it only for named accounts or devices that need it, such as meeting room or kiosk devices.
  2. Review Entra ID sign-in logs for recent device code authentications by users who do not normally use them, especially sign-ins from unfamiliar IPs or countries.
  3. For any suspected compromised account, revoke sessions and refresh tokens, reset credentials, and check for new mailbox rules, MFA methods and device registrations.
  4. Tell users that an unexpected Teams or meeting-booking page asking them to enter a code at a Microsoft sign-in page is a phishing indicator, and give them a way to report it.

What happened

CVE-2026-111497, nicknamed Node2Shell, is an out-of-bounds write in the Google Brotli decoder that a remote, unauthenticated attacker can trigger with a crafted compressed stream, causing memory disclosure, denial of service or possibly code execution. Siemens advisories republished by CISA say the Node.js project shipped fixes on 21 October 2026 and list affected Desigo CC, Gridscale X, RUGGEDCOM APE1808 (PAN-OS based) and Industrial Edge products. Microsoft has updated its guide with affected Windows versions and the November 2026 security updates. The CVE is in CISA KEV and the story is tagged as exploited in the wild, but none of the advisories describe the attacks.

Why it matters

Brotli is embedded in Node.js, .NET, Python bindings, Linux distributions and appliances such as PAN-OS, so any internet-facing service that decompresses attacker-supplied Brotli data may be reachable. The flaw is in KEV with no stated due date, public proof-of-concept code exists and EPSS is 82.6%, so treat patching as urgent. Severity figures differ: Siemens gives CVSS 9.8 and other scoring gives 9.2.

What to do

  1. Install the Microsoft November 2026 Windows and .NET security updates, prioritizing internet-facing servers.
  2. Update Node.js runtimes to the 21 October 2026 security releases and update bundled or standalone Brotli libraries to 1.0.10, 1.1.1 or 1.2.1.
  3. Upgrade PAN-OS on firewalls (including RUGGEDCOM APE1808) to the fixed release Palo Alto Networks specifies and apply its workarounds meanwhile.
  4. Apply Siemens updates for Gridscale X and Industrial Edge apps, and Siemens' interim mitigations where no fix exists; restrict network access to OT management interfaces.
  5. Hunt for Node.js and web worker processes spawning shells or unexpected crashes on exposed services.

What happened

According to Siemens advisories republished by CISA on 12 November 2026, the PHP project and researchers disclosed two critical unauthenticated remote code execution flaws in the core PHP runtime on 21 October 2026, dubbed PHP2Shell (CVE-2026-109618 and CVE-2026-109619). The first involves request memory left uninitialized when PHP aborts on out-of-memory errors. The second involves global state that still points to freed request memory, which later requests can read. Both are listed in CISA KEV, and public proof-of-concept code exists. Downstream impact includes Palo Alto Networks PAN-OS, which runs on Siemens RUGGEDCOM APE1808, and many Siemens building automation and energy products.

Why it matters

Any internet-facing PHP application, and appliances that embed PHP such as PAN-OS firewalls and Panorama, may be open to unauthenticated code execution. Both CVEs are on CISA KEV, public exploit code exists, and EPSS is 99.999% for each, so expect broad scanning and exploitation. No KEV due date is given. Severity scores differ between sources: NVD gives CVE-2026-109618 a CVSS of 9.2, while the Siemens advisories rate both at CVSS 3.1 9.8.

What to do

  1. Inventory every internet-facing PHP application and appliance, including PAN-OS firewalls and Panorama, and apply PHP or vendor fixes immediately.
  2. Apply the workarounds from Palo Alto Networks' PHP2Shell notices to PAN-OS devices until fixed builds are installed, and restrict management interface exposure to trusted networks.
  3. For Siemens energy and building automation products without fixes, isolate them behind firewalls following Siemens operational guidelines, and track Siemens advisory updates.
  4. Hunt for PHP worker processes spawning shells or download utilities, and for new script files in web roots, on Windows and Linux web servers.
  5. Treat any confirmed compromise of an appliance as full device compromise. Rotate credentials and secrets stored on it, and review VPN and admin sessions.

wfx-loot campaign used 4,837 compromised GitHub accounts to push secrets-stealing malware

GitHub GitHub · 1 source · first reported 12 November 2026

What happened

BleepingComputer reports a campaign it calls wfx-loot, in which attackers used 4,837 compromised GitHub accounts to probe 61,764 repositories, open pull requests and push malware built to steal secrets, with cloud credentials as the stated goal. The available reporting does not describe how the accounts were compromised, how the malware works, which repositories or organizations were affected, or any indicators of compromise.

Explainer

Background, not news

Device code phishing: abusing the OAuth device authorization grant

Device code phishing tricks a user into entering an attacker-generated code on Microsoft's real sign-in page, which hands the attacker valid tokens for the user's account, MFA included.

Why today. Huntress describes attackers dressing up device code phishing as a Microsoft Teams meeting-booking flow, so victims complete a genuine Microsoft sign-in that authorizes the attacker's session. Knowing how the flow works shows why the usual phishing advice (check the URL, use MFA) does not stop it, and which controls and logs do. See story 1.

How the device code flow is meant to work

The OAuth 2.0 device authorization grant, standardized in RFC 8628, exists for devices that cannot easily show a browser or take a password: smart TVs, printers, command-line tools. The device asks the identity provider for a device code and a short user code, then tells the user to visit a verification page on another device and type the user code in. In Microsoft Entra ID that page is Microsoft's own device login page.

While the user signs in on that page, including any MFA prompt, the original device keeps polling the token endpoint. Once the user finishes, the token endpoint issues an access token and a refresh token to whoever holds the device code. The codes are short-lived; Microsoft documents a lifetime of about 15 minutes.

How attackers turn it into phishing

The weakness is that the party who starts the flow and the person who approves it do not have to be the same, and the approval page does not reliably show the user which device or person they are authorizing. An attacker starts the flow from their own infrastructure, usually with the client ID of a legitimate Microsoft first-party public app, and gets a user code. They pass that code to the victim with a pretext such as joining a meeting, verifying an identity or, in this case, completing a Teams booking.

The victim goes to a real Microsoft domain, sees a real Microsoft page, enters the code and approves MFA. Nothing about the URL looks wrong, because nothing is wrong with it. The tokens go to the attacker's polling client. The short code lifetime is why these campaigns rely on live, interactive lures: the victim has to act within minutes of the attacker generating the code.

What the attacker gains

The attacker holds a refresh token as well as an access token, so access lasts well beyond the original session and survives the victim closing their browser. Depending on the client ID used, the refresh token can often be exchanged for tokens to other Microsoft resources such as Exchange Online, SharePoint, Teams or Microsoft Graph, giving mail, file and directory access. Changing the user's password does not on its own invalidate every issued refresh token; sessions have to be revoked explicitly. Security researchers have also shown the technique being extended to register attacker devices in Entra ID, which can make access more persistent.

What it looks like in telemetry

In Entra ID sign-in logs, device code sign-ins are labeled with an authentication protocol of device code. In Microsoft Sentinel you can filter SigninLogs on the AuthenticationProtocol column for deviceCode, and the Defender XDR advanced hunting sign-in tables carry similar fields. Most users never use this flow, so any device code sign-in for an ordinary office worker, rather than an admin running a CLI tool, deserves a look.

Follow-up activity usually shows up as non-interactive sign-ins (AADNonInteractiveUserSignInLogs in Sentinel) as the attacker redeems the refresh token, often from hosting-provider or VPN IP addresses and from client apps the user does not normally use. Look for a device code sign-in followed shortly by mailbox access, inbox rule creation, Graph API activity or new device registrations for that account.

How to prevent it

The most effective control is a Conditional Access policy using the authentication flows condition to block device code flow for everyone, with narrow exclusions only for users, devices or locations that genuinely need it, such as meeting-room devices or specific admin workstations. Microsoft recommends blocking device code flow wherever it is not required. Pair this with user awareness that is specific: a real colleague or meeting service will never ask you to type a code into the Microsoft device login page.

For defenders

  1. Create a Conditional Access policy that blocks the device code authentication flow for all users, run it in report-only mode first to find legitimate use, then enforce it with narrowly scoped exclusions.
  2. Hunt the last 30 days of SigninLogs for AuthenticationProtocol equal to deviceCode and review every account that is not a known admin or shared device, especially sign-ins followed by non-interactive token use from unfamiliar IP addresses.
  3. When a device code compromise is confirmed, revoke the user's sessions and refresh tokens, not just the password, and check for newly registered devices, inbox rules and app consents on the account.
  4. Alert on device code sign-ins for high-value users such as executives, finance staff and admins, and on new device registrations that follow a device code sign-in.
  5. Update phishing awareness material to state that entering a code on the Microsoft device login page at someone else's request grants them access, even though the site is genuine.
