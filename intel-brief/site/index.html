What happened

Microsoft's November 2026 Patch Tuesday fixed CVE-2026-124194, a spoofing flaw in classic Outlook (CVSS 6.5) that Microsoft says is being exploited in the wild. CISA added it to the Known Exploited Vulnerabilities catalog on 10 November 2026. Rapid7 reports that opening a specially crafted file makes Outlook silently connect to an attacker-controlled location and leak the user's NTLMv2 hash, which can be cracked or relayed live to services lacking SMB/LDAP signing or Extended Protection. Sources disagree on the release's total size, with counts ranging from about 1,092 to 1,260 fixes.

Why it matters

Outlook runs on nearly every Windows endpoint, and leaked NTLMv2 hashes give attackers a path to impersonate users against file servers, LDAP and other internal services. The flaw is confirmed exploited, CISA's federal remediation deadline is 24 November 2026, and public proof-of-concept code is reported to exist, although Rapid7 says there was no public disclosure before release. No EPSS score is available yet. Rapid7 notes the moderate CVSS score understates its value for both mass credential harvesting and targeted intrusions.

What to do

  1. Deploy the November 2026 Office and Microsoft 365 Apps updates to all classic Outlook installations before 24 November 2026, and confirm update channels have picked up the build.
  2. Block outbound SMB (TCP 445 and 139) from endpoints to the internet at the perimeter and host firewall to stop hash leakage to external hosts.
  3. Add high-value accounts to the Protected Users group and restrict outbound NTLM where possible to blunt captured-hash abuse.
  4. Enforce SMB signing, LDAP signing and channel binding, and Extended Protection for Authentication to reduce NTLM relay risk.
  5. Hunt for Outlook-initiated SMB or WebDAV connections to public addresses, and reset passwords for affected users if any are found.

What happened

On 10 November 2026, CISA added two Barracuda Networks flaws to its Known Exploited Vulnerabilities catalog. CVE-2026-116606 (CVSS 9.3) is an authentication bypass in Email Security Gateway (ESG). It lets an unauthenticated remote attacker call a configuration-import function and restore a crafted backup archive, which changes the appliance's global configuration. CVE-2026-111560 (CVSS 8.6) is an OS command injection in a timezone value that runs commands as root; CISA says it affects ESG plus Load Balancer, ADC, Message Archiver, WAF Control Center, WAF and Web Security Gateway, and that the two flaws can be chained.

Why it matters

CISA lists both flaws as exploited in the wild, and chained together they could plausibly let an unauthenticated attacker run root commands on an internet-facing mail gateway that sees all inbound mail. Public proof-of-concept code is reported for the authentication bypass (EPSS 1.6%; 1.1% for the command injection). The KEV remediation due date is 13 November 2026, only three days after the listing.

What to do

  1. Apply Barracuda's mitigations and updates for both CVEs on all ESG and other affected Barracuda appliances before the 13 November 2026 KEV deadline, or take exposed appliances offline if no mitigation is available.
  2. Restrict the ESG administrative interface so it is not reachable from the internet, allowing only trusted management networks.
  3. Review ESG configuration, admin accounts, timezone settings and configuration-import or restore history for changes you cannot explain, and follow CISA's forensics triage guidance on any appliance that was exposed.
  4. Treat any appliance showing tampering as compromised: rebuild or replace it, and rotate credentials and keys stored on or passing through it, including LDAP and SMTP relay credentials and admin passwords.
  5. Check outbound traffic from the appliance's IP for unusual destinations, and review mail-flow and routing rules for unauthorized changes.

Huntress details four evolving ClickFix attack chains, including lateral movement and PNG-hidden payloads

1 source · first reported 10 November 2026

What happened

Huntress reports that ClickFix, a social engineering technique that tricks users into pasting and running attacker-supplied commands, has evolved. According to Huntress, recent chains add lateral movement, payloads hidden inside PNG image files, Node.js-based remote access trojans, and a browser cache abuse technique. The available summary does not give indicators, specific malware families, or victim details.

Why it matters

ClickFix gets around many email and download controls because the user runs the command themselves, usually through the Windows Run dialog or a terminal, so any Windows endpoint with a human user is exposed. Huntress says the activity now goes beyond a single host to lateral movement, which raises the impact of one successful lure. No CVE or patch applies, so detection and user controls are the main defenses.

What to do

  1. Hunt for Run dialog (RunMRU) entries and explorer.exe-spawned shells that contain PowerShell, mshta, curl or encoded commands, and investigate any hits.
  2. Hunt for node.exe running from user-writable paths such as AppData or Temp and making outbound connections, which may indicate a Node.js RAT.
  3. Where business needs allow, restrict the Win+R Run dialog for standard users through Group Policy and enable Attack Surface Reduction rules that block obfuscated scripts and Office or script child processes.
  4. After any confirmed ClickFix execution, check for lateral movement from the affected host and rotate the user's credentials.
  5. Brief users that legitimate sites never ask them to paste commands into Run, PowerShell or a terminal to fix errors or pass CAPTCHA checks.

Explainer

Background, not news

NTLM hash leakage and relay: how a file can hand over a user's credentials

NTLM hash leakage happens when Windows is made to authenticate automatically to an attacker's server, exposing a challenge-response that can be cracked offline or relayed live to another service as that user.

Why today. The exploited Outlook zero-day in today's lead story works by making Outlook silently connect to an attacker-controlled location and send the user's NTLMv2 response. Whether that becomes a cracked password or a relayed login depends on controls most environments have only partly deployed. See story 1, story 9, story 7.

How the leak works

NTLM is a challenge-response protocol. When a Windows client connects to a server that asks for NTLM, the client proves it knows the user's password hash by answering a server-chosen challenge, without sending the password itself. Windows will often do this automatically and silently for resources it treats as reachable, such as a UNC path over SMB or a WebDAV location over HTTP.

Coerced-authentication bugs abuse this. A crafted email, document or file contains a reference to a remote path the attacker controls. When the client processes it, Windows reaches out and performs the NTLM handshake with the attacker's server, which records the NTLMv2 response. No code runs on the victim and no prompt appears, so a medium-severity spoofing or information disclosure label can understate the risk.

Cracking versus relaying

The captured NTLMv2 response can be attacked offline: the attacker guesses passwords and checks each guess against the response. Strong, long passwords make this impractical, while weak or reused ones fall quickly. Machine accounts and managed service accounts with long random passwords are effectively uncrackable this way.

Relaying is the more dangerous outcome because password strength does not matter. The attacker forwards the victim's handshake in real time to a different server, such as a file server, LDAP on a domain controller, AD CS web enrollment or another HTTP service, and is authenticated there as the victim. Relay succeeds only where the target does not bind the authentication to the session: SMB without required signing, LDAP without signing or channel binding, and HTTP services without Extended Protection for Authentication.

What it looks like in telemetry

The leak itself is an outbound connection from a user process to an unusual destination. In Defender XDR, look in DeviceNetworkEvents for Outlook or other Office processes connecting to TCP 445 or to HTTP/WebDAV on public IP addresses, and in DeviceProcessEvents or service events for the WebClient service starting unexpectedly. On endpoints with NTLM outbound auditing enabled, the Microsoft-Windows-NTLM/Operational log records outgoing NTLM authentication attempts with the target server name.

A successful relay shows up on the target: a network logon (event 4624, logon type 3) using NTLM for a user, arriving from an IP address that is not that user's workstation, often followed by LDAP changes, certificate requests or file access the user would not normally perform. Defender for Identity has detections for suspected NTLM relay and NTLM authentication anomalies against domain controllers.

How to shut it down

Patch the coercion bug first, but treat the class as permanent: new coercion paths appear regularly. The durable fix is to make leaked handshakes useless. Block outbound SMB to the internet at the perimeter and on host firewalls, require SMB signing on servers and clients, enforce LDAP signing and channel binding on domain controllers, and enable Extended Protection on IIS, Exchange and AD CS web endpoints. Defaults differ by Windows and Exchange version, so verify the effective setting rather than assuming it.

Reduce NTLM use itself. Put privileged accounts in the Protected Users group, which prevents them from using NTLM, and use the Restrict NTLM group policies in audit mode first to find what still depends on NTLM before blocking outgoing NTLM to remote servers.

For defenders

  1. Deploy the November 2026 Outlook update for the exploited spoofing flaw and confirm coverage of classic Outlook installs, since it is in CISA KEV.
  2. Hunt in DeviceNetworkEvents for OUTLOOK.EXE and other Office processes connecting to public IPs on port 445 or over WebDAV, and confirm outbound SMB to the internet is blocked at the edge and on host firewalls.
  3. Verify SMB signing is required on file servers and domain controllers, and that LDAP signing and channel binding are enforced on every domain controller.
  4. Enable Extended Protection for Authentication on Exchange, AD CS web enrollment and other internal IIS services that accept Windows authentication.
  5. Add admin and other high-value accounts to Protected Users, and turn on NTLM outbound auditing to inventory remaining NTLM dependencies before restricting it.
