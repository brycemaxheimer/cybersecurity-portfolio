What happened

On 24 November 2026 CISA added three vulnerabilities to its Known Exploited Vulnerabilities catalog, citing evidence of active exploitation. CISA describes CVE-2026-132165 as a Drupal Core flaw that can let an unauthenticated attacker abuse the installer (install.php) to reinstall Drupal under specific conditions, taking over the site or running arbitrary code. CVE-2026-131914 is an unauthenticated remote code execution flaw caused by unsafe deserialization in the Idunno AntiCsrf library, which CISA says may be end-of-life. The vulnerability data also lists this product as blowdart anticsrf. CVE-2026-132224 is a flaw in the Optimizely Web Experimentation account signup flow that CISA says lets attackers impersonate customer users, change Project JavaScript and serve malicious script to visitors of affected sites.

Why it matters

All three are being exploited, and federal agencies must remediate by 27 November 2026. The AntiCsrf flaw is rated CVSS 9.3 (EPSS 4.3%) and the Drupal flaw has public proof-of-concept code, so any internet-facing Drupal site or .NET web app using AntiCsrf is a direct path to server compromise. The Optimizely issue is a hosted-service supply-chain risk: injected JavaScript can run in your users' browsers without any change to your own servers.

What to do

  1. Inventory internet-facing Drupal sites and apply the vendor's Drupal Core security update now. Until then, block external access to install.php and confirm the installer cannot run on production sites.
  2. Find .NET applications that reference the Idunno or blowdart AntiCsrf package. Move to a supported version or remove the library, since CISA notes it may be end-of-life.
  3. If you use Optimizely Web Experimentation, review Project JavaScript and recent account and user changes for unauthorized edits. Follow Optimizely's mitigation guidance.
  4. On Drupal and IIS hosts, hunt for web server processes spawning shells and for unexpected changes to Drupal settings files, following CISA's forensic triage guidance.
  5. Treat any confirmed exploitation as a full host compromise. Rotate database and application credentials on affected servers.

What happened

Rapid7 published an analysis of CVE-2026-123890, a critical (CVSS 9.8) flaw in the VMware vCenter directory service. An unauthenticated attacker who can reach DCE/RPC on TCP 2012 can obtain the session key of a login the attacker starts and complete it as an SSO administrator without the password. Rapid7 reproduced the bypass on vCenter Server Appliance 8.0.2.00400 and turned it into root command execution. The chain copied the directory database, took the STS signing key, forged an administrator session, created a local superAdmin account and enabled SSH. SecurityWeek reports that VMware has shipped updates fixing this vCenter bypass along with critical ESX code execution flaws, but the sources do not list fixed builds.

Why it matters

vCenter controls the whole virtualization estate, including Windows servers and domain controllers running as VMs, and theft of the STS signing key lets an attacker forge trusted admin sessions even after the bypass is patched. The CVE is in CISA's KEV catalog (no due date given), public proof-of-concept code exists, and EPSS is 5.0%, so treat any vCenter with TCP 2012 reachable from untrusted networks as urgent.

What to do

  1. Apply VMware's vCenter updates for CVE-2026-123890 now; take the fixed build numbers from VMware's advisory, because the sources do not state them.
  2. Until patched, use firewall rules to block TCP 2012, 443 and 22 to vCenter from everything except dedicated admin hosts.
  3. Check each vCenter appliance for compromise: unexpected local superAdmin or appliance accounts, SSH or Bash being enabled, and unexplained SSO administrator logins.
  4. If compromise is suspected, treat the STS signing key and directory database as stolen. Rebuild or replace the STS certificates and rotate SSO, root and service account credentials according to VMware guidance.
  5. Review the ESX vulnerabilities fixed in the same release and patch ESX hosts too.

Newly formed Inception extortion group runs large-scale vishing campaign against SSO credentials

1 source · first reported 24 November 2026

What happened

BleepingComputer reported on 24 November 2026 that a newly formed data extortion group calling itself Inception has been linked to a large-scale voice phishing (vishing) campaign. According to the report, the campaign targets single sign-on (SSO) credentials at multiple global brands and companies. The available reporting does not name the identity providers, the specific social engineering pretexts, the victims, or any indicators of compromise.

Why it matters

SSO accounts give access to every application behind the identity provider, including Microsoft 365 and Entra ID-federated SaaS, so one phone call that captures a password and MFA approval can lead straight to data theft and extortion. Exploitation is confirmed in the wild, and no software patch applies; defenses depend on help desk procedures, phishing-resistant MFA and close monitoring of sign-ins and MFA changes. Because the sources give few technical details, defenders should hunt for generic vishing follow-on activity rather than specific indicators.

What to do

  1. Brief the help desk and staff that callers posing as IT or the help desk may ask for SSO credentials, MFA codes or MFA resets, and require out-of-band identity verification before any password or MFA reset.
  2. Enforce phishing-resistant MFA (FIDO2 or Windows Hello for Business) for privileged and high-value users and restrict who can register new MFA methods using Conditional Access, for example only from compliant devices or trusted locations.
  3. Review recent MFA method registrations, password resets and new device enrollments, and confirm each was expected with the user.
  4. Hunt for successful sign-ins from unfamiliar IP addresses or countries shortly after credential or MFA changes, and for bulk data access or downloads in SharePoint, OneDrive and other SSO-connected SaaS applications.
  5. For any suspected compromise, revoke sessions and refresh tokens, reset credentials, and remove attacker-registered MFA methods and devices.

Explainer

Background, not news

Forged tokens from stolen signing keys: why one private key can be every admin

When an identity service signs authentication tokens with a private key, anyone who steals that key can mint valid tokens for any user, with no password, MFA or login event.

Why today. Rapid7's vCenter chain did not stop at the authentication bypass: it copied the directory database, took the STS signing key and forged an administrator session. That last step explains why patching alone does not undo a compromise. See story 2.

How token signing works

Federated and single sign-on systems do not re-check a password every time a user reaches a service. A token service authenticates the user once, then issues a signed assertion, such as a SAML token, saying who the user is and what groups they belong to. Relying services check the signature against a certificate they trust and accept the claims inside.

In vCenter, the vSphere SSO Secure Token Service (STS) issues these tokens, and its signing material lives in the VMware Directory Service. In Microsoft environments, AD FS signs SAML tokens with its token-signing certificate, and Entra ID trusts that certificate for federated domains. The design is the same in both: the signing key is the root of trust for every session.

What an attacker gains

With the private key, an attacker can write a token for any identity, including built-in administrators, add any group claims, and sign it so the relying service accepts it. This is the technique publicly described as Golden SAML. It was used against AD FS in the SolarWinds-era intrusions.

Forged tokens skip the identity provider's login. No password is checked, MFA is never prompted, and conditional checks that run at the identity provider may never fire. The key stays valid until it is replaced. Patching the bug that exposed it, or resetting user passwords, does not invalidate tokens the attacker can keep minting.

What it looks like in telemetry

The forged sign-in itself often looks normal to the relying service. Look for the gap instead: a session at the service with no matching authentication event at the token issuer. For AD FS-federated Entra ID tenants, that means federated sign-ins in Entra logs without corresponding AD FS token issuance events. Defender for Identity can also alert on suspicious reads of the AD FS key material in Active Directory.

On vCenter, the forged session is usually followed by noisier actions. Watch for new local SSO or superAdmin-type accounts, SSH or the shell being enabled on the appliance, unexpected access to or export of the directory database, and administrative logins from unfamiliar sources. Forward vCenter and appliance logs to Sentinel so these events survive an attacker with root.

Recovery and prevention

If a signing key may have been exposed, treat it as burned. Replace the STS signing certificate using VMware's documented certificate replacement procedure. For AD FS, Microsoft's compromise guidance calls for rolling the token-signing certificate twice, so the previous certificate cannot be reused. Then remove persistence the attacker created with their forged access.

Prevention means treating token issuers as tier-zero. Restrict network reach to their management and directory ports, limit who can log in, and monitor key access. Where it fits, reduce dependence on on-premises federation, for example by moving Entra ID domains from AD FS to cloud authentication.

For defenders

  1. If any vCenter was reachable on TCP 2012 before patching for CVE-2026-123890, assume the STS signing key may be exposed. Replace it following VMware's guidance after patching.
  2. Audit vCenter for SSO or local accounts created recently, SSH or shell enablement, and admin logins from unexpected hosts. Send those logs to Sentinel.
  3. In Sentinel, correlate Entra ID federated sign-ins with AD FS token issuance events and alert on sign-ins that have no matching issuance.
  4. Confirm Defender for Identity sensors are deployed on AD FS servers and review any alerts about AD FS key material access.
  5. Inventory every system whose signing key can mint admin sessions, such as AD FS, vCenter STS and other SSO providers. Restrict network access to them as tier-zero assets.
