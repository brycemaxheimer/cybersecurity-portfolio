What happened

On 19 November 2026 Broadcom published VMSA-2026-0009, fixing CVE-2026-123890 (CVSS 9.8), an authentication bypass in the VMware Directory Service component of vCenter Server. According to Rapid7, an unauthenticated attacker with network access to vCenter can gain access as the Administrator user. Mandiant reported the flaw, and Google Threat Intelligence says China-linked espionage group ARMORY CASTLE exploited it as a zero-day as early as September 2026, as BleepingComputer and SecurityWeek also report. Rapid7 notes this bug is separate from CVE-2026-59309, an earlier 2026 vCenter authentication bypass, and Broadcom says systems already patched for that earlier flaw still need the new update.

Why it matters

vCenter controls the whole virtualization estate, including domain controllers and other Windows servers running as VMs, so Administrator access gives an attacker broad control and a place to hide outside endpoint telemetry. CVE-2026-123890 is confirmed exploited in the wild and listed in CISA KEV, though no KEV due date is given. Public proof-of-concept code is reported for both CVEs (EPSS 0.8% for CVE-2026-123890, 22.9% for CVE-2026-59309), and Broadcom offers no workaround.

What to do

  1. Upgrade every vCenter Server as an emergency change to 8.0 U3m, 9.0.2.0200, 9.1.1.0200 or VCF 5.2.5 as applicable. Use the standard update mechanism, because Broadcom says vCenter Quick Patch cannot apply these fixes. Include systems already patched for CVE-2026-59309.
  2. For vCenter 7.0 extended-support deployments, contact Broadcom Support for the fix. Until it is applied, restrict network access to vCenter management and directory service ports to dedicated admin hosts.
  3. Before upgrading, review Broadcom's FAQ and interoperability matrix for the Back-in-Time restriction, which blocks moving from 8.0 U3m or 9.0.2.0200 to VCF 9.1.1. Plan for the vCenter management interfaces being briefly unavailable.
  4. Treat vCenter instances that were reachable from untrusted networks since September 2026 as potentially compromised. Review the vCenter and SSO logs for Administrator sessions you cannot explain, new local accounts, role changes, and VM snapshot, clone or export activity.
  5. After patching, rotate vCenter SSO Administrator and service account credentials, and check that no unauthorized changes were made to ESXi hosts.

What happened

Microsoft published an entry in its Security Update Guide on 19 November 2026 for CVE-2026-111497, a buffer overflow in Google's Brotli decompression decoder. The entry contains no technical detail, affected version ranges or fix information. The vulnerability is rated CVSS 9.2 (critical) and appears in the CISA Known Exploited Vulnerabilities catalog, so exploitation in the wild is reported, and public proof-of-concept code is said to exist. Products linked to the CVE include Google Brotli, Node.js, brotlicffi, Microsoft .NET and Debian Linux.

Why it matters

Brotli is embedded in web servers, reverse proxies, runtimes and browsers, so the decoder may be reachable wherever untrusted compressed content is processed, including .NET and Node.js applications on Windows servers. With KEV listing, EPSS 82.4% and public proof-of-concept code, treat this as urgent even though CISA has not set a due date and the sources do not give affected or fixed versions.

What to do

  1. Check the Microsoft Security Update Guide entry for CVE-2026-111497 and apply the .NET updates Microsoft lists for it as soon as they are available.
  2. Inventory every component that bundles Brotli: .NET runtimes, Node.js, Python brotli or brotlicffi packages, Debian hosts, and internet-facing proxies or gateways. Update each to the vendor's fixed release.
  3. Prioritize internet-facing services that decompress client-supplied Brotli content, such as web apps, API gateways and reverse proxies. Where you cannot patch quickly, consider disabling Brotli request decompression on those services.
  4. Monitor web-facing processes such as w3wp.exe, node.exe and dotnet.exe for crashes or unexpected child processes, which could indicate exploitation attempts.

No. 03 · Priority 51

Rapid7: Webworm APT hides access with a disguised custom SoftEther VPN bridge

SoftEther VPN · 1 source · first reported 19 November 2026

What happened

Rapid7 reports that the China-aligned group Webworm, already known for planting the open-source SoftEther VPN in compromised government networks, appears to have moved to a modified SoftEther VPN Bridge build designed to evade security tools. Rapid7 attributes the tool to Webworm with moderate confidence. It is a 64-bit Windows binary based on SoftEther VPN Bridge version 4.44 build 9807, rebranded in its PE metadata with OriginalFileName netcapa.exe, the description Network Monitor Software and the company name Network Systems Solutions Inc. Rapid7 says it knows of only one public sample, and the excerpt does not describe how initial access was gained.

Why it matters

The tool contains no conventional malware code, so it gives long-term, low-profile network access that signature-based tools may miss. Any SoftEther component on Windows servers or endpoints where it was not deliberately deployed should be treated as a possible intrusion foothold. Rapid7 reports active use against government organizations, but no prevalence figures or CVEs are involved.

What to do

  1. Hunt for processes or files with OriginalFileName netcapa.exe, or with the company name Network Systems Solutions Inc. and the description Network Monitor Software.
  2. Inventory all SoftEther VPN components (vpnbridge, vpnserver, vpnclient) across Windows hosts and investigate any instance not sanctioned by IT.
  3. Block or alert on unapproved VPN and tunneling software through application control (WDAC or AppLocker) and Defender for Endpoint custom indicators.
  4. Review outbound connections from servers to unusual external hosts on ports that SoftEther commonly uses, and confirm that long-lived tunnels are legitimate.
  5. If you find a disguised bridge, isolate the host, collect the binary and its configuration for analysis, and investigate the account and method used to install it.

No. 06 · Priority 51

Huntress details MSP incident where one compromised account led to two rogue ScreenConnect deployments

ScreenConnect · 1 source · first reported 19 November 2026

What happened

Huntress published an incident response write-up describing a case handled with managed service provider TruePath IT, where a single compromised account was used to set up two unauthorized ScreenConnect remote access deployments. According to Huntress, the incident caused about $3M in downtime and was first surfaced through RMM alerts during the night. The available summary does not say how the account was compromised, which systems were reached, or what the attackers did after gaining remote access.

Why it matters

Attackers increasingly use legitimate remote monitoring and management tools such as ScreenConnect for persistence and hands-on access, because the binaries are signed and often allowed by policy. One stolen account with rights to deploy software or log in remotely can be enough to push an attacker-controlled instance across many endpoints, which is especially dangerous for MSPs and their customers. Exploitation in this case is confirmed, but the sources give no indicators, so detection depends on spotting ScreenConnect instances and relay hosts your organization does not own.

What to do

  1. Inventory every ScreenConnect client on endpoints and servers and compare the relay host in each client service command line against your organization's approved instances; remove and investigate any that do not match.
  2. Enforce application control so that only approved RMM tools and approved ScreenConnect instances can install or run.
  3. Require phishing-resistant MFA and review recent sign-ins for accounts that can deploy software, administer RMM platforms, or access customer environments.
  4. Alert on new RMM service installations and on RMM processes spawning shells, and make sure off-hours alerts are triaged rather than queued.
  5. If a rogue instance is found, isolate affected hosts, reset credentials for the compromised account and any accounts used during remote sessions, and review session activity for lateral movement or data staging.

Huntress details network-based detection for Timeroasting by parsing MS-SNTP authenticator formats

1 source · first reported 19 November 2026

What happened

On 19 November 2026 Huntress published research on detecting Timeroasting, a technique that abuses Microsoft's MS-SNTP time protocol to obtain material from domain controllers that can be cracked offline to recover computer account passwords. Huntress notes that Timeroasting produces no authentication log entry, but says it is still observable. According to Huntress, it reverse-engineered the two authenticator forms used in MS-SNTP requests so that detection does not depend on packet size, which an attacker can alter. The available excerpt does not include the full detection logic, specific signatures or tooling details.

Why it matters

Every Active Directory domain controller answers MS-SNTP requests by default, so all Windows domains are exposed. The main risk is computer accounts with weak or predictable passwords, such as pre-created or legacy accounts, whose cracked credentials give an attacker a foothold. No exploitation in the wild is tied to this research, but because the technique leaves no Windows security log, defenders need network visibility to see it.

What to do

  1. Find computer accounts with non-default or predictable passwords, such as pre-created or legacy pre-Windows 2000 compatible accounts and accounts whose password has not rotated in a long time, and reset them.
  2. Restrict inbound UDP 123 to domain controllers so only expected clients and subnets can reach it, and log that traffic at the network layer.
  3. Alert on non-time-service processes on endpoints that send NTP traffic to domain controllers, for example scripting runtimes or unknown binaries.
  4. Baseline NTP request volume per source to each domain controller and investigate sources that send bursts of requests.
  5. Review the Huntress research for its authenticator-format detection logic and adapt it to your network sensors (IDS or NDR).

Background, not news

vCenter as a tier-zero asset: why owning the management plane equals owning the estate

VMware vCenter Server centrally controls every ESXi host and virtual machine it manages, so an attacker with vCenter administrator rights effectively controls every workload in the virtual estate, including domain controllers.

Why today. Broadcom's fix for CVE-2026-123890, an unauthenticated vCenter authentication bypass that Google says a China-linked espionage group exploited as a zero-day since September 2026, hands an attacker exactly this level of control. It helps to understand what vCenter Administrator access means and why it so often goes unseen. See story 1.

What vCenter and its directory service are

vCenter Server is the management layer for vSphere. It manages ESXi hosts, and through them every virtual machine, datastore, virtual network and snapshot. Most organisations deploy it as the vCenter Server Appliance, a Linux-based virtual appliance that sits outside the Windows estate and its endpoint agents.

Authentication to vCenter runs through vCenter Single Sign-On, which is backed by the VMware Directory Service (vmdir). That is an LDAP-style directory holding the local SSO domain (vsphere.local by default), its users and groups, and the built-in Administrator account. A flaw in that component, like the one Rapid7 describes as an authentication bypass via an alternate path, undermines the root of trust for the whole vSphere deployment, not a single feature.

What an attacker gains

With vCenter Administrator rights an attacker can power VMs on and off, open VM consoles, create new VMs, change virtual networking, and take snapshots, clones or exports of any guest. For a Windows estate, the critical consequence is that a snapshot or clone of a domain controller can be copied off and its Active Directory database and registry hives read offline. That yields domain credential material without running anything on the domain controller itself.

vCenter administrators can also manage the ESXi hosts beneath it. Public incident reporting on espionage groups targeting VMware, including Mandiant's, describes attackers using this position to plant persistence on hypervisors and to run rogue or hidden VMs. Both are places where Windows-centric EDR has no visibility. That is why espionage actors value the management plane: it offers broad access, long dwell time and little telemetry.

What it looks like in telemetry

Defender XDR will usually see nothing on the appliance or hosts themselves, so detection depends on forwarding vCenter and ESXi logs into Sentinel. Useful signals are vCenter events for VM snapshot, clone, export and console sessions, especially against domain controllers and other tier-zero servers. Others are changes to SSO users, groups and identity sources, new local accounts, enabling of SSH or the ESXi shell, and logins from unusual source addresses or at unusual times.

An authentication bypass may never produce a failed-login trail, so look for its effects rather than the login itself. Administrator activity that does not line up with change tickets is one example, as are snapshots of sensitive VMs that no backup job created. On the Windows side, new interactive or service logons using credentials that could only have come from an offline copy of Active Directory are a downstream clue.

How to reduce the risk

Patching is necessary but not sufficient. Exploitation reportedly began in September, so treat vCenter instances that were reachable during that window as possibly compromised and review them, not just update them. Network isolation matters most: vCenter's web, API and directory interfaces should be reachable only from dedicated administrative hosts, never from user networks or the internet.

Manage vSphere as tier zero. Use separate administrative identities that are not ordinary domain accounts, keep the vsphere.local Administrators group minimal, and protect domain controller VMs with features such as VM encryption where your licensing and version support it. Exact capabilities differ between vSphere versions, so confirm them against Broadcom's documentation for your release.

For defenders

  1. Apply the fixed builds from VMSA-2026-0009 to every vCenter Server, including instances already patched for CVE-2026-59309, since Broadcom says that earlier fix does not cover the new flaw.
  2. Restrict network access to vCenter management and directory interfaces to a dedicated administrative network or jump hosts, and confirm no vCenter is reachable from the internet.
  3. Forward vCenter and ESXi logs to Sentinel. Alert on snapshots, clones, exports and console sessions involving domain controllers, and on SSH or ESXi shell being enabled.
  4. Audit vsphere.local users, groups and identity sources for accounts or membership changes made since September 2026, and investigate any you cannot tie to a change record.
  5. If vCenter compromise cannot be ruled out, assume domain controller VMs may have been copied, and plan krbtgt and privileged credential resets as part of the response.
