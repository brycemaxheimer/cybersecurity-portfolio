What happened

SANS ISC reports that Microsoft's November 2026 Patch Tuesday, released 10 November 2026, addresses 1,260 vulnerabilities. Of these, 68 are rated critical and 167 are Chromium issues affecting Edge. According to SANS ISC, the Outlook spoofing vulnerability CVE-2026-124194 is already being exploited. Other notable fixes include a critical LDAP remote code execution flaw (CVE-2026-119958), several critical Microsoft Message Queuing and Queue Manager flaws (CVE-2026-109459, CVE-2026-119967, CVE-2026-116710, CVE-2026-119963, CVE-2026-119964), and a Windows TCP/IP remote code execution flaw (CVE-2026-113859) that carries a CVSS score of 7.5.

Why it matters

CVE-2026-124194 is listed in CISA KEV, public proof-of-concept code exists, and its EPSS is 1.6%. No KEV due date is given, and the sources do not describe how the spoofing is triggered or what attackers gain from it. The LDAP flaw CVE-2026-119958 has CVSS 9.8, EPSS 1.3% and public proof-of-concept code, which puts domain controllers and other LDAP-exposed servers at risk. MSMQ hosts reachable on the network should also be patched quickly.

What to do

  1. Deploy the November 2026 Office and Microsoft 365 Apps updates for CVE-2026-124194 first, because it is exploited in the wild.
  2. Patch domain controllers and other servers exposed to LDAP for CVE-2026-119958 (CVSS 9.8, public PoC).
  3. Patch hosts running Microsoft Message Queuing, and block TCP 1801 at the perimeter or disable MSMQ where it is not needed.
  4. Apply the Windows cumulative update for CVE-2026-113859 (TCP/IP RCE) across endpoints and servers.
  5. Use Defender Vulnerability Management to confirm patch coverage, and track remaining exposure to these CVEs.

Microsoft: multiple threat actors deploy GSocket for persistent C2 on compromised Linux servers

GSocket · 1 source · first reported 11 November 2026

What happened

Microsoft reports several incidents in which threat actors installed GSocket, an open source remote access tool, on Linux servers after exploiting web application vulnerabilities. According to Microsoft, the tool let attackers keep access after the original vulnerabilities were patched. Defender for Endpoint telemetry shows the activity growing over recent months, concentrated on web applications and hosting environments. Microsoft notes that GSocket traffic goes through the public Global Socket Relay Network, so attackers need no infrastructure of their own.

Why it matters

Patching an exploited web application does not evict an attacker who has already installed GSocket. Both ends connect outbound to a shared public relay, so there is no attacker-owned IP address or domain to block, and the host needs no inbound listener. Any Linux web or hosting server in your estate that was compromised and then only patched may still be under attacker control, and the sources describe exploitation as confirmed and widespread.

What to do

  1. On any Linux web server with a past or suspected application compromise, check for GSocket binaries, processes and persistence before declaring the incident remediated.
  2. Hunt for GSocket tool names (gs-netcat, gsocket, gs-sftp, gs-mount) in process and file telemetry across Linux devices onboarded to Defender for Endpoint.
  3. Review cron jobs, systemd units, shell profile files and authorized_keys on affected hosts for persistence, and check for signs of privilege escalation.
  4. Restrict outbound traffic from servers to the Global Socket Relay Network at the egress firewall or proxy, as Microsoft suggests, and alert on attempts to reach it.
  5. Rebuild confirmed-compromised hosts where possible and rotate credentials and secrets stored on them.

No. 04 · Priority 64

Rogue ScreenConnect clients pushed to MSP customer endpoints in active campaign

ConnectWise ScreenConnect · 2 sources · first reported 11 November 2026

What happened

BleepingComputer reported on 11 November 2026 that ConnectWise is investigating an active malware campaign against managed service providers. Attackers are using compromised ScreenConnect environments to install rogue remote-access clients on customer devices, and dozens of organizations are affected. Huntress, writing on 12 November 2026, describes the activity as a worm it calls SCKit. According to Huntress, it uses cloud-hosted ScreenConnect panels to install rogue ScreenConnect clients and session cookie relays across hundreds of managed endpoints. Neither source names a CVE, and neither gives details on how the panels were first compromised.

Why it matters

Exploitation is confirmed and widespread. Any organization whose MSP uses ScreenConnect may already have an attacker-controlled remote-access client running alongside, or instead of, the legitimate one. These clients are signed, legitimate software, so they often get past antivirus and give the attacker interactive, SYSTEM-level access that persists after the original panel is cleaned up. The session cookie relays Huntress mentions also point to a risk of browser session or token theft affecting M365 and other cloud accounts.

What to do

  1. Inventory every ScreenConnect client service on your endpoints and confirm each relay host it connects to belongs to your own or your MSP's approved instance; isolate devices that report to unknown instances.
  2. Contact your MSP to confirm whether their ScreenConnect environment is affected by the campaign ConnectWise is investigating, and ask for their list of legitimate instance hostnames.
  3. Uninstall unauthorized ScreenConnect clients and block unapproved ScreenConnect relay domains at the proxy and firewall.
  4. On affected hosts, revoke and reissue browser sessions and refresh tokens for signed-in users (for example by revoking Entra ID sessions), because Huntress reports that session cookie relays were deployed.
  5. Restrict remote-access tool installation with application control so that only approved RMM instances can run.

Attackers run self-hosted AntiFox AI pentest agents on Alibaba Cloud to steal AWS credentials

AntiFox · 1 source · first reported 11 November 2026

What happened

BleepingComputer reports that attackers are hosting their own instances of AntiFox, an open-source agentic penetration testing platform, on Alibaba Cloud infrastructure. According to the report, they use these instances to target web services and AWS environments in order to steal AWS credentials. The available reporting is brief. It does not name victims, specific vulnerabilities, indicators of compromise or the exact techniques the AI agents use.

Why it matters

Agentic pentest tooling lets attackers automate reconnaissance and credential harvesting against internet-facing web applications at scale. Any public web service in your estate that holds or can reach AWS credentials is a potential target, including keys stored in config files, environment variables or instance metadata. Exploitation is confirmed in the wild, but no indicators have been published, so defenders must rely on behavior and exposure review.

What to do

  1. Inventory internet-facing web applications that store AWS access keys, or can retrieve them from environment variables, config files or instance metadata. Move them to short-lived role credentials where possible.
  2. Enforce IMDSv2 on AWS EC2 instances so that server-side request forgery from a web app cannot easily read role credentials.
  3. Review AWS CloudTrail and Defender for Cloud Apps for access key use from unfamiliar cloud provider IP ranges, including Alibaba Cloud. Rotate any keys used unexpectedly.
  4. Look in web server and WAF logs for high-volume automated scanning that probes for exposed secrets such as .env files, configuration backups and cloud credential files.
  5. Remove long-lived IAM user access keys that are not needed and apply least privilege to those that remain.

Explainer

Background, not news

Legitimate remote access software as attacker persistence and C2

Attackers install or hijack real remote management and remote access tools so their control channel looks like normal IT administration traffic and survives the removal of their original entry point.

Why today. The SCKit campaign pushes rogue ScreenConnect clients to MSP-managed endpoints, and Microsoft describes attackers using the open source GSocket tool, relayed through a public network, to keep access to Linux servers after the original flaws were patched. Both are the same playbook: a trusted, signed or open source tool in place of custom malware. See story 4, story 2, story 5.

How the technique works

MITRE ATT&CK tracks this as Remote Access Software (T1219). Instead of writing a custom implant, the attacker installs a legitimate remote monitoring and management (RMM) or remote access product, such as ScreenConnect, AnyDesk or a similar agent, or an open source tunnelling tool like GSocket. The tool is configured to call out to a server or relay the attacker controls or can use.

There are two common variants. In the first, the attacker installs a new agent that reports to their own instance, for example a trial or cloud-hosted panel. In the second, which is what SCKit appears to exploit, the attacker compromises a legitimate management panel the victim or its provider already trusts and uses it to push extra clients or run commands across every endpoint it manages.

Why attackers prefer it

These tools are often code-signed by a known vendor, are widely allowlisted, and are designed to run as a service, start at boot and reconnect on their own. That gives persistence and interactive control without the attacker writing or maintaining malware, and many antivirus products do not flag them because they are legitimate software.

The connections are outbound, usually over HTTPS or to vendor or public relay infrastructure, so they pass through firewalls that only block inbound traffic. With relay-based tools like GSocket, the attacker needs no server of their own and there is no fixed attacker IP address to block. Because the access does not depend on the original vulnerability, patching the entry point leaves the backdoor in place.

What it looks like in telemetry

On Windows, look for remote access agents installed as new services, executables running from unusual paths, or a second instance of a product you already use. ScreenConnect clients typically install as a service whose name includes a unique instance identifier, so an unfamiliar identifier next to your sanctioned one is a strong signal. In Defender XDR, DeviceProcessEvents, DeviceFileEvents, DeviceRegistryEvents and DeviceNetworkEvents together show the installer, the new service, and the outbound connection to the relay host.

The relay hostname is often more telling than the binary. A sanctioned RMM agent talks to your tenant's known host. A rogue agent talks to a different instance or a different vendor's cloud. On Linux, watch for long-lived processes making outbound connections to public relay networks and for new cron, systemd or shell profile entries that relaunch them.

How to prevent and contain it

Define which remote access products are allowed and enforce it with application control, such as App Control for Business or AppLocker, plus Defender for Endpoint indicators that block unsanctioned tools. Restrict egress so only approved RMM relay hosts are reachable from endpoints and servers.

Treat RMM consoles and MSP access as privileged identities: require phishing-resistant MFA, limit who can deploy agents or run scripts at scale, and review console audit logs. After any compromise, inventory every remote access agent and scheduled relaunch mechanism before declaring the host clean, because removing the initial exploit does not remove these.

For defenders

  1. Build an inventory of every remote access and RMM product running across your estate using Defender for Endpoint software inventory and process data, and flag any vendor or instance identifier you did not deploy.
  2. Alert on new services or processes from remote access vendors whose outbound connections go to hosts other than your sanctioned RMM instance, joining DeviceProcessEvents with DeviceNetworkEvents.
  3. Block unapproved remote access tools with application control policy and file or certificate indicators, and restrict endpoint and server egress to approved relay hosts.
  4. If you use an MSP, confirm with them which agents and consoles touch your environment, how console access is protected, and whether they have reviewed for rogue ScreenConnect clients this week.
  5. On Linux web servers, hunt for persistent outbound processes, new cron or systemd entries, and connections to public relay networks, especially on hosts that previously had an exploited web vulnerability.
