Microsoft 365 token theft via phishing kits and device code phishing remains active

Microsoft Microsoft 365 · 3 sources · first reported 17 November 2026

What happened

Huntress researchers describe how the EvilTokens, Knight Office and Kali365 phishing kits capture Microsoft 365 session tokens and replay them, as reported by BleepingComputer on 17 November 2026. Huntress also says Defender incident data helped it uncover a token-replay campaign affecting 97 accounts at 79 organizations. Microsoft says device code phishing, where a victim is persuaded to enter an attacker-initiated code on a legitimate sign-in page, has become a recurring route to account takeover. Microsoft says it worked with industry and law enforcement to disrupt EvilTokens in September 2026, and it published lab research showing a phished GitHub device-code approval could be abused against GitHub Copilot CLI, which it stresses has not been observed in the wild.

Why it matters

Token theft and device code phishing bypass passwords and often MFA, so a single user approval or proxied sign-in gives attackers access to mail, files and other cloud services until the tokens are revoked. Huntress reports confirmed in-the-wild token replay across dozens of organizations, and Microsoft notes that any public client supporting the OAuth device flow can be abused the same way, including developer tooling and AI coding agents.

What to do

  1. Block or restrict the device code authentication flow with Entra ID Conditional Access authentication flow policies, allowing it only for named users or devices that need it.
  2. Require compliant or hybrid-joined devices and token protection where supported for Microsoft 365 access to reduce the value of replayed tokens.
  3. For any account with suspected token theft, revoke sessions and refresh tokens, reset credentials, and review new inbox rules, OAuth consents and registered MFA methods.
  4. Review sign-in logs for device code authentications and for sessions used from unfamiliar IP addresses or countries shortly after a legitimate sign-in.
  5. Review GitHub organization policy for Copilot CLI remote control and device-flow sign-ins, and audit access to private repositories for affected developers.

What happened

CISA republished two Siemens advisories on 17 November 2026 covering CVE-2026-111497, nicknamed Node2Shell. It is an out-of-bounds write in the Brotli decoder that ships with Node.js, which the Node.js project patched on 21 October 2026. According to the advisory text, Google Brotli 1.0.3 through 1.2.0 is affected, and a crafted Brotli-compressed stream lets a remote unauthenticated attacker corrupt memory, leak memory contents, crash the process or possibly run code. Siemens lists dozens of affected industrial and engineering products, including Teamcenter, Opcenter, Polarion-related tools and SIMATIC WinCC. Fixes are available for some of these products, and Siemens offers mitigations for the others.

Why it matters

The CVE is in CISA KEV, exploitation in the wild is confirmed, public proof-of-concept code exists, and EPSS is 82.6%. CVSS is 9.2, and Siemens rates it 9.8. Any Windows or Linux server running Node.js or another product that bundles a vulnerable Brotli library and decompresses untrusted input should be treated as exposed. That includes web apps, internal tools and vendor appliances, and the sources also name .NET and Debian packages.

What to do

  1. Inventory Node.js runtimes and bundled Brotli libraries on servers, prioritizing internet-facing services. Apply the Node.js security releases of 21 October 2026 and the patched Brotli versions.
  2. Update Siemens products where Siemens has released fixes. Apply Siemens' recommended mitigations for products still awaiting fixes, and restrict network access to them.
  3. Patch other bundlers named in the CVE data, such as .NET, Debian brotli packages and brotlicffi, as vendor updates become available.
  4. Hunt for Node.js processes spawning shells or scripting engines, and for unexpected crashes of Node.js services, which may indicate exploitation attempts.
  5. Until patched, consider rejecting Brotli-encoded request bodies from untrusted sources at reverse proxies or WAFs.

What happened

CISA added CVE-2026-115731, a deserialization of untrusted data flaw in Perforce Puppet Enterprise, to its Known Exploited Vulnerabilities catalog on 17 November 2026, citing evidence of active exploitation. According to CISA, the bug sits in Puppet's report-processing code: any client holding a CA-signed agent certificate can run arbitrary code on the Puppet Server as the service user by submitting a specially crafted report. CISA warns that if the Puppet certificate authority signs requests automatically without strong verification, an unauthenticated network attacker can obtain a valid certificate and exploit the flaw. The sources do not list affected or fixed version numbers.

Why it matters

A Puppet Server pushes configuration and code to every managed node, including Windows servers and endpoints, so compromising it can lead to fleet-wide code execution and credential theft. The flaw is rated CVSS 9.4, public proof-of-concept code exists, and exploitation is confirmed, even though EPSS is only 0.7%. CISA set a federal remediation due date of 1 December 2026 and asks agencies to check for compromise before patching.

What to do

  1. Apply Perforce's mitigations and updates for CVE-2026-115731 on all Puppet Servers and compile servers now, ahead of CISA's 1 December 2026 due date.
  2. Disable or tighten certificate autosigning: remove naive or wildcard autosign rules and require policy-based verification, so attackers cannot obtain agent certificates.
  3. Review the full list of signed agent certificates and revoke any you cannot tie to a known managed node.
  4. Restrict network access to the Puppet Server agent port (8140 by default) to known managed networks; never expose it to the internet.
  5. Perform compromise triage on Puppet Servers. Check for unexpected child processes, files or outbound connections from the Puppet Server service user. Also review recent catalog and code changes that could have pushed malicious changes to managed Windows and Linux nodes.

No. 04 · Priority 59

Phishing kit on Google Cloud Storage harvests mail passwords and the victim domain's MX record

1 source · first reported 17 November 2026

What happened

SANS ISC describes a phishing email built around a password-expiry lure. Its link pointed to an HTML page on Google Cloud Storage, with the recipient's address carried in the URL fragment. The page shows a login form branded with the recipient's domain and uses the thum.io screenshot service to pull the organization's real website in as a background image. Under several layers of URL encoding and JavaScript obfuscation, SANS found a multi-language credential-harvesting kit. It collects the password, public IP, geolocation, browser details and language, plus a field labeled "MX Record", and sends them to the attacker through the Telegram Bot API. The available text is cut off before it explains how the MX lookup works, so its exact purpose is not confirmed by the sources.

Why it matters

Collecting the victim domain's MX record tells the attacker which mail provider the organization uses, such as Microsoft 365. That lets them prioritize stolen credentials and target follow-on sign-in attempts. The lure is generic and hosted on a trusted cloud domain, so URL-reputation filtering may not stop it. Any captured Entra ID credentials should be treated as live for account-takeover attempts.

What to do

  1. Search mail logs for messages linking to HTML files on storage.googleapis.com, and purge matching messages from mailboxes.
  2. For any user who clicked, reset the password, revoke sessions and review Entra ID sign-ins for unfamiliar IPs or locations.
  3. Alert on browser traffic to api.telegram.org bot endpoints and to the thum.io screenshot service from corporate endpoints.
  4. Require phishing-resistant MFA and Conditional Access so stolen passwords alone cannot complete a sign-in.
  5. Remind users that password-expiry emails linking to externally hosted login pages are a common phishing pattern.

Explainer

Background, not news

Client-side supply chain attacks: third-party JavaScript, CSP and SRI

A client-side supply chain attack compromises a script that a website loads from a vendor, so the malicious code runs in every visitor's browser with the full privileges of the site that included it.

Why today. Attackers abused Optimizely Experimentation to inject malicious JavaScript into 178 major websites, and Unit 42's OPTIMJACK analysis describes the same pattern of a compromised vendor script exposing the sites that load it. See story 6, story 8.

How borrowed scripts become an attack path

Most large websites load JavaScript from outside parties: analytics, A/B testing, tag managers, chat widgets and ad tech. A script tag that points at a vendor's domain tells the browser to fetch whatever that vendor serves at that moment and run it in the page. The site owner does not review each version, and many of these scripts are designed to change often, because experimentation and tag platforms let marketing teams push new code without a site deployment.

The browser applies the same-origin policy by the origin of the page, not the origin of the script. Vendor code included with a script tag therefore runs as if the site wrote it. If an attacker compromises the vendor, a vendor account, or a vendor configuration path, every site that includes the script serves the attacker's code with no change to its own servers. This is the model behind Magecart-style card skimming, and it is why one vendor compromise can reach hundreds of sites in a single day.

What the attacker gains

Injected code can read and change anything on the page. It can capture form fields such as card numbers and passwords, read cookies that are not marked HttpOnly, rewrite displayed content such as cryptocurrency payment addresses, and send the data to attacker servers. It can also fingerprint visitors and selectively deliver further exploits, as in the Optimizely case where outdated iPhones and iPads were served iOS exploit kits.

For the site owner this is a breach of customer data without any intrusion into their own infrastructure. For an enterprise defender it also means trusted, well-known websites can become a delivery channel to employee devices, so reputation-based web filtering offers little protection.

Where CSP and SRI help, and where they don't

Content Security Policy is a response header that tells the browser which sources may supply scripts and which destinations the page may connect to. A host-based allowlist does not stop malicious code served from an allowed vendor domain, which is the common case in this kind of attack. Its stronger value is in restricting where data can be sent (connect-src, form-action, img-src) so a skimmer has fewer exfiltration paths, and in its reporting feature, which sends violation reports that can reveal unexpected sources or destinations.

Subresource Integrity adds a cryptographic hash to a script tag, and the browser refuses to run the file if the content does not match. It is very effective for static, versioned libraries. It does not work for scripts that legitimately change on every publish, such as experimentation snippets and tag managers, so those need other controls: self-hosting a reviewed copy where the vendor allows it, limiting which pages load them, keeping them off checkout and login pages, and protecting the vendor accounts that can push code.

What it looks like in telemetry

Detection on the site side mainly comes from CSP violation reports, client-side script monitoring that tracks changes in script content and behavior, and comparison of served JavaScript against known-good versions. Server logs usually show nothing because the malicious content never touches the site's own infrastructure.

On the endpoint side, Defender for Endpoint network events may show browsers connecting to newly registered or unusual domains straight after visits to reputable sites, and Defender SmartScreen or network protection blocks may appear on otherwise trusted browsing. When a vendor compromise is disclosed, the indicators the vendor or researchers publish are the most practical hunting starting point, because the domain used to deliver the code is legitimate.

For defenders

  1. Inventory every third-party script your public websites load, including through tag managers and experimentation platforms, and record who can publish code through each vendor account.
  2. Keep third-party marketing and experimentation scripts off login, payment and account pages, and add Subresource Integrity hashes to any static third-party library you continue to load.
  3. Deploy Content Security Policy with tight connect-src and form-action directives, start in report-only mode, and send violation reports somewhere your team actually reviews them.
  4. Enforce MFA and least privilege on vendor consoles such as Optimizely, tag managers and CDNs, and review their audit logs for unexpected publishes.
  5. When a vendor compromise is disclosed, hunt in Defender XDR for browser connections to the published exfiltration and exploit domains, and prioritize patching of outdated mobile devices managed through Intune.
