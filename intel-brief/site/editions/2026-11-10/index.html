Scanning for SAP NetWeaver CVE-2025-31324 webshells continues, per SANS ISC honeypots

SAP NetWeaver · 1 source · first reported 9 November 2026

CVE-2025-31324

CISA KEV

What happened

SANS ISC reported on 9 November 2026 that its honeypots are receiving requests for webshell paths such as ant.jsp under the SAP NetWeaver /irj/servlet_jsp/irj/root/ directory, along with requests to the vulnerable metadata uploader endpoint. These requests are tied to CVE-2025-31324, an unauthenticated file upload flaw rated CVSS 10.0. According to SANS, one source address (82.26.72.21) is probing a broad list of upload and webshell paths across many products, including SharePoint, Joomla extensions, Samsung MagicInfo and WhatsUp Gold, alongside SAP. SANS frames the activity as attempts either to exploit NetWeaver or to find webshells that earlier attackers already planted.

Why it matters

CVE-2025-31324 is in CISA KEV, has public proof-of-concept code and an EPSS of 99.5%, so any unpatched internet-facing NetWeaver Visual Composer instance should be assumed at risk or already compromised. Scanners checking for existing webshells means earlier compromises can be reused by new actors, so patching alone is not enough without a compromise check. The same scanner also targets SharePoint and other upload endpoints, which may be present on edge-facing Windows servers.

What to do

  1. Apply SAP's security fix for CVE-2025-31324 to all NetWeaver systems, prioritizing those reachable from the internet, or block access to the /developmentserver/metadatauploader endpoint until patched.
  2. Inspect the /irj/servlet_jsp/irj/root/ directory and related NetWeaver web directories for unexpected .jsp, .java or .class files and treat any found as a compromise.
  3. Review web server and reverse proxy logs for requests to the metadatauploader endpoint and to ant.jsp or other unknown JSP files, and for traffic from 82.26.72.21.
  4. Hunt for shells or reconnaissance commands spawned by the NetWeaver Java server processes.
  5. If a webshell is found, isolate the host, rotate SAP service and connected credentials, and investigate lateral movement.

What happened

On 9 November 2026 CISA added four vulnerabilities to its Known Exploited Vulnerabilities catalog, citing evidence of active exploitation. According to CISA, CVE-2026-102895 in GPUStack lets an unauthenticated attacker gain administrative access, create persistent admin API keys, expose worker and cloud-provider secrets, and execute code through the inference-backend import endpoint. CVE-2026-123158 is an authentication bypass in OpenSSH on Linux, and CVE-2026-116779 is a code injection flaw in SignalWire FreeSWITCH that can lead to credential disclosure, call control and command execution. CVE-2026-123218 in IBM Aspera Faspex lets an authenticated user bypass authorization and escalate privileges. The sources do not name affected or fixed versions or describe the attackers.

Why it matters

All four flaws are confirmed exploited and carry a federal remediation due date of 12 November 2026. The OpenSSH bypass is the broadest exposure: it affects internet-facing Linux servers and appliances, has public proof-of-concept code and an EPSS of 16.5%. GPUStack AI servers, FreeSWITCH VoIP systems and Aspera Faspex file-transfer portals are often exposed to the internet, and exploitation can hand over full control or leak cloud credentials (EPSS 0.6%, 2.2% and 0.7% respectively).

What to do

  1. Inventory internet-facing Linux hosts running OpenSSH and apply the vendor or distribution fix for CVE-2026-123158 by 12 November 2026. Until patched, restrict SSH to VPN or allow-listed source addresses.
  2. Patch or take offline any exposed GPUStack, FreeSWITCH and IBM Aspera Faspex instances according to vendor guidance, and block internet access to GPUStack and FreeSWITCH management interfaces.
  3. On GPUStack, review admin accounts and API keys for unexpected creation, revoke unknown keys, and rotate worker and cloud-provider secrets stored in the platform.
  4. On FreeSWITCH, rotate SIP and configuration credentials, and review the host for unexpected child processes and call-routing changes.
  5. Follow CISA's forensics triage expectation: check each affected system for signs of compromise from before the patch, not only after it.

Explainer

Background, not news

Webshells: persistent backdoors planted through web server vulnerabilities

A webshell is a small script file dropped into a web application's served directory that lets an attacker run commands on the server by sending ordinary HTTP requests to it.

Why today. SANS honeypots show attackers still hunting for SAP NetWeaver webshells planted through CVE-2025-31324, and Huntress found hidden webshells left on exploited AhsayCBS backup servers. In both cases the webshell outlives the original flaw. See story 1, story 7.

How a webshell works

A webshell is a script in whatever language the server executes, such as JSP on Java application servers, ASPX on IIS, or PHP on many Linux stacks. Once it sits in a directory the server serves, any HTTP request to its path makes the server run it with the privileges of the web application process. A typical webshell takes a command or file operation from a request parameter, runs it, and returns the output in the response.

Attackers usually plant webshells by abusing an unauthenticated file upload, a path traversal, or a code execution bug. CVE-2025-31324 is the textbook case: the SAP NetWeaver Visual Composer metadata uploader accepted files without authentication, and attackers used it to write JSP files into the portal's servlet_jsp/irj/root directory, where the server would execute them.

Why patching does not remove it

The vulnerability is only the delivery route. Once the file is on disk, the webshell is a standalone backdoor that needs no exploit, so applying the vendor fix closes the door but leaves anything already planted in place. That is why SANS sees requests for known webshell names like ant.jsp: scanners are checking whether an earlier attacker's shell is still answering, which is cheaper than exploiting the bug again.

Webshells are also commonly used to drop second-stage tools. The Huntress AhsayCBS findings, with cryptominers and a Python command-and-control implant alongside the shells, fit that pattern: the webshell is the foothold, and the follow-on payloads do the long-term work.

What it looks like in telemetry

The strongest endpoint signal is the web server or application server process spawning a command interpreter or reconnaissance tool. On Windows that means processes such as w3wp.exe, or the Java process hosting an application server, launching cmd.exe, powershell.exe, whoami.exe or similar. On Linux, look for the Java or web server process starting sh or bash. In Defender XDR this shows up in DeviceProcessEvents with the server process as InitiatingProcessFileName.

The second signal is script files created in web-served directories by the server process itself, visible in DeviceFileEvents. In web access logs, watch for requests to newly appearing script paths that return success, especially from a small set of source addresses, and for successful POST requests to upload endpoints that should not be reachable from the internet. Many webshells are tiny and evade antivirus signatures, so behavior matters more than file hashes.

Prevention and response

Keep administrative and upload components off the internet where possible, patch exposed application servers quickly, and restrict write permissions so the service account cannot write into executable web directories. File integrity monitoring on web roots catches new script files that signatures miss.

If you find a webshell, treat the host as compromised rather than simply deleting the file. Check for additional shells, scheduled tasks, new accounts, dropped binaries and credential access performed through the shell, and review what that server's service account could reach.

For defenders

  1. Inventory internet-facing SAP NetWeaver Java systems, confirm the CVE-2025-31324 fix is applied, and check whether the Visual Composer metadata uploader is reachable from the internet.
  2. Search the NetWeaver servlet_jsp/irj/root directory and other web roots for JSP, ASPX or PHP files that do not belong to the vendor installation, and compare against a known-good baseline.
  3. Hunt in DeviceProcessEvents for web and application server processes (w3wp.exe, Java-based servers, Apache, nginx) spawning cmd.exe, powershell.exe, sh, bash, whoami or other recon tools.
  4. Alert in DeviceFileEvents on script files created in web-served directories by the server's own process.
  5. When a webshell is found, scope the whole host for follow-on payloads such as miners, implants, new accounts and scheduled tasks before deciding whether to rebuild.
