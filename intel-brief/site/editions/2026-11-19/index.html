What happened

On 18 November 2026 CISA added four vulnerabilities to its Known Exploited Vulnerabilities catalog, citing evidence of active exploitation. CISA describes all four as allowing remote code execution. CVE-2024-10441 is an output-escaping flaw in the system plugin daemon of Synology DSM and BeeStation OS. CVE-2026-40217 is an unprotected alternate channel in BerriAI LiteLLM reachable through the /guardrails/test_custom_code endpoint, CVE-2026-90817 is an unauthenticated code injection in Vanderbilt REDCap that requires a valid public survey hash, and CVE-2026-90436 is an unsafe reflection flaw in Apache Axis triggered by a crafted SOAP fault message, which CISA notes may affect end-of-life versions.

Why it matters

All four are rated CVSS 8.8 to 9.8, public proof-of-concept code exists for each, and CISA confirms exploitation. LiteLLM AI gateways (EPSS 61.9%) and REDCap research servers (EPSS 25.2%) are often internet-facing and run outside standard patch cycles; Synology NAS (EPSS 2.2%) and legacy Java services embedding Axis (EPSS 1.8%) are frequently forgotten assets. Federal agencies must remediate the Synology, REDCap and Axis flaws by 21 November 2026 and LiteLLM by 2 December 2026.

What to do

  1. Inventory internet-facing LiteLLM proxies, REDCap servers, Synology NAS devices and Java applications bundling Apache Axis, and remove them from direct internet exposure where possible.
  2. Apply vendor fixes for Synology DSM/BSM, LiteLLM and REDCap per vendor guidance; for Apache Axis, migrate off end-of-life versions or decommission the service if no mitigation exists.
  3. Block or restrict access to the LiteLLM /guardrails/test_custom_code endpoint at the reverse proxy or WAF until patched, and limit LiteLLM admin APIs to trusted networks.
  4. Treat exposed unpatched hosts as potentially compromised: review web logs and process trees for shells or downloaders spawned by Python, Java or PHP service processes, as CISA's forensics triage guidance expects.
  5. Rotate API keys and model provider credentials stored in LiteLLM, and credentials on any REDCap or Axis host where suspicious activity is found.

  • Apache Axis: versions not stated; CISA says affected products may be end-of-life

What happened

What to do

  1. Find out whether your organization or its suppliers use Wellington IT, and ask the provider for incident details, scope and indicators.
  2. If you have a relationship with the provider, review and restrict its remote access, and rotate any credentials or API keys it holds.
  3. Warn staff and customers that member data may be used in targeted phishing or fraud, and tighten checks on account-change and payment requests.
  4. Watch for official notifications from the provider, the affected credit unions or regulators that confirm the scope and the data exposed.

No. 05 · Priority 47

Two malicious versions of Microsoft's Agent Framework PyPI package stole cloud credentials

Microsoft Agent Framework · 1 source · first reported 18 November 2026

What happened

BleepingComputer reported on 18 November 2026 that attackers compromised Microsoft's official Agent Framework Python package on PyPI. The attackers published two malicious versions built to steal cloud credentials and other sensitive data from developer systems. The available reporting does not name the malicious version numbers, the infection mechanism, the exfiltration endpoints, or how long the versions stayed available.

Why it matters

Developer workstations, build agents and CI/CD runners that install or update Python dependencies could have pulled a malicious release. That would expose cloud keys, Entra ID service principal secrets and tokens stored on those hosts. Theft is reported as confirmed, so treat any host that installed the package during the exposure window as compromised until you can prove otherwise.

What to do

  1. Inventory every developer machine, build server, container image and lockfile that references the Microsoft Agent Framework Python package. Find which versions were installed and when, and check them against Microsoft's or PyPI's list of malicious releases once it is published.
  2. On any host that installed a malicious version, rotate all credentials reachable from it. This covers cloud access keys, Azure and Entra ID service principal secrets, managed identity tokens, API keys, and secrets in environment variables or CLI credential caches.
  3. Pin the package to a version Microsoft confirms is clean, and block or yank the malicious versions in any internal package mirror or proxy.
  4. Review Entra ID sign-in and audit logs and cloud provider activity logs for unusual use of credentials tied to affected developers or pipelines, starting from the install date.
  5. Require hash-pinned, lockfile-based dependency installs in CI so a new upstream release cannot be pulled in silently.

Cisco Talos tracks UAT-12643 infostealer campaign using Solana blockchain for C2 resilience

1 source · first reported 18 November 2026

What happened

Cisco Talos reported on 18 November 2026 that it is tracking a financially motivated group it calls UAT-12643, whose tools include the Go-based Overlord RAT, a Python infostealer the actor calls Good Game, and a clipboard hijacker that targets several cryptocurrencies. According to Talos, the Overlord variant hides encrypted command-and-control server addresses in Solana blockchain transaction memos. Lures include a trojanized Viber installer, payloads named after the MicroSIP softphone, and a decoy financial statement PDF. Talos links the actor to North Korea with only low confidence, based on overlapping tradecraft and on earlier use of Overlord by the UNK_DeadDrop cluster and of Solana-memo C2 by Lazarus.

Why it matters

The lures are aimed at finance and accounting staff, call-center or VoIP softphone users, messaging users, and cryptocurrency or gaming account holders. Talos says the document harvesting targets English, French, Spanish and Portuguese file names, which points to European victims. Because the C2 addresses are fetched from a public blockchain, blocking servers alone will not cut the channel; outbound traffic to Solana services from unexpected processes is a more durable signal. The available excerpt lists no CVEs and no indicators, and no vulnerability patching applies.

What to do

  1. Hunt for non-browser, non-wallet processes on Windows endpoints that resolve or connect to Solana blockchain services, and investigate any unsigned binaries you find.
  2. Review recent executions of Viber or MicroSIP installers or binaries launched from Downloads or Temp folders, and confirm they came from legitimate vendor sources.
  3. Block or alert on Python interpreters running from user-writable paths on finance and call-center workstations where Python is not an approved tool.
  4. Retrieve the Talos indicators of compromise from the full report and sweep network, DNS and file telemetry for them.
  5. Warn finance, accounting and call-center staff about financial-statement PDF lures and unofficial messaging or softphone installers.

What happened

On 18 November 2026, Rapid7 and F5 disclosed CVE-2026-123007 (CVSSv4 9.2), an integer underflow in nginx HTTP/2 flow-control handling. Rapid7 says a remote, unauthenticated client can corrupt memory, which can leak data, crash the service, or run code with the permissions of the nginx worker process. Rapid7 built a proof-of-concept that achieved RCE against nginx 1.31.8 in a linux/amd64 Docker image with HTTP/2 and TLS enabled. Rapid7 labels the issue fixed, but the sources do not name the fixed release.

Why it matters

nginx is common on internet-facing reverse proxies, gateways and appliances, so exposure is likely wide. Rapid7 says exploitation is hard in practice: it takes about 128 GB of HTTP/2 traffic, needs more than roughly 300 Mbit/s of bandwidth to finish within nginx's default one-hour connection lifetime, usually fails when HTTP/2 is proxied upstream, and the known technique depends on AVX-512 glibc memcpy paths. There is no known exploitation and the CVE is not in CISA KEV, but public PoC work exists and EPSS is 6.4%, so patch exposed HTTP/2 listeners promptly.

What to do

  1. Find every internet-facing nginx instance, including those embedded in appliances and containers, and apply F5's fixed nginx release for CVE-2026-123007 as soon as F5 publishes the version.
  2. Until patched, consider disabling HTTP/2 on exposed listeners, or terminate HTTP/2 at an upstream proxy or CDN, which Rapid7 says likely prevents the attacker-controlled frames from reaching nginx intact.
  3. Shorten HTTP/2 connection lifetimes and rate-limit or alert on single client connections that send very large amounts of HTTP/2 data.
  4. Watch nginx worker processes for unexpected child processes such as shells, and for repeated worker crashes or restarts.
  5. Rebuild container images that bundle vulnerable nginx versions once a fix is available.

Background, not news

Blockchain dead drops: hiding C2 addresses on public ledgers

A blockchain dead drop is a command-and-control technique in which malware reads its next server address from data stored on a public blockchain, so defenders cannot take it down or edit it.

Why today. Cisco Talos reports that UAT-12643's Overlord RAT pulls encrypted C2 addresses from Solana transaction memos, and Talos published separate research on why these on-chain dead drops are hard to disrupt. See story 6.

How a dead drop resolver works

A dead drop resolver separates the malware from its real C2 server. The implant does not hardcode the server address. It contacts a legitimate, trusted service, reads a value the operator placed there, and decodes that value into the current C2 address. MITRE ATT&CK tracks this as Dead Drop Resolver (T1102.001) under Web Service.

For years the drop sat on platforms such as paste sites, social media profiles or code repositories. Those can be reported and removed. Public blockchains remove that option. Data written to a ledger cannot be deleted, no provider can suspend it, and anyone can read it.

Talos describes several on-chain variants: Bitcoin transaction data, EVM smart contracts (the approach publicly called EtherHiding), TRON wallets, and Solana memos. On Solana, the Memo program attaches arbitrary text to a transaction. An operator writes an encrypted address into a memo sent from a wallet they control, and the malware queries that wallet's recent transactions to find it.

What the attacker gains

The main gain is resilience. If defenders sinkhole or seize a C2 server, the operator sends one new transaction with a fresh address, and every infected host picks it up on its next lookup. Neither the implant nor the existing infections need to change.

Reading the drop is a read-only query to a public RPC node or a block explorer API. It usually costs the malware nothing and needs no wallet. The traffic goes to infrastructure that many organizations never block, often over HTTPS to large shared providers. Encrypting the memo also means a defender who reads the chain sees only an opaque string unless they have recovered the key from a sample.

What it looks like in telemetry

The lookup itself is the best detection point, because the real C2 address changes and the resolver does not. Watch for processes that have no reason to talk to blockchains making DNS queries or HTTPS connections to public RPC endpoints or explorer APIs. Examples include script interpreters, freshly dropped binaries in user-writable paths, installers, and Go or Python executables with no known publisher. Shortly after, the same process typically connects to an address that was never seen in DNS beforehand.

In Defender XDR, DeviceNetworkEvents and DeviceEvents with DNS query data let you group blockchain-related destinations by InitiatingProcessFileName, folder path and signer. On most corporate endpoints, browsers and approved crypto or developer tools are the only expected callers. Treat anything else as worth triage, especially if it was launched from an installer or document lure like those Talos describes.

Why takedowns fail, and what still works

You cannot remove the record, and blocking a single wallet only helps until the operator moves to a new one. Blocking all blockchain RPC traffic may be acceptable on general user endpoints but can break legitimate workloads elsewhere, so scope it by device role.

Durable controls work around the drop rather than against it. Block the initial execution, through application control and attack surface reduction rules that stop unsigned binaries from user-writable paths. Alert on the resolver behavior described above. Use the operator wallet as a hunting pivot: once a sample reveals which wallet it reads, threat intelligence teams can watch that wallet for new memos and learn about new C2 addresses as soon as the operator publishes them.

For defenders

  1. Build a Defender XDR hunting query that flags non-browser, unsigned or user-path processes resolving or connecting to public blockchain RPC and explorer domains, and baseline which tools legitimately do so.
  2. Where the business has no blockchain use, block or alert on blockchain RPC and explorer categories at the web proxy or DNS layer for standard user endpoints.
  3. Correlate a blockchain lookup with a follow-on connection from the same process to a raw IP or newly seen domain within minutes; that pair is a strong dead drop signal.
  4. Enforce application control or ASR rules that block executables launched from Downloads, Temp and AppData, which stops trojanized installers like the fake Viber and MicroSIP payloads Talos describes.
  5. When a sample is recovered, extract the wallet it reads and add it to threat intelligence monitoring so new C2 addresses are detected when published.
