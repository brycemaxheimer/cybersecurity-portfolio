FBI warns attackers are using the ARTEX AI penetration testing framework in global attacks

ARTEX · 1 source · first reported 15 November 2026

What happened

According to BleepingComputer, the FBI has warned that threat actors are using ARTEX, an AI-powered penetration testing framework, to automate attacks against organizations worldwide. BleepingComputer reports that the activity includes a recent supply-chain breach involving ConnectWise that led to compromised Microsoft 365 customer environments. The available reporting does not describe ARTEX's techniques, indicators of compromise, or how the ConnectWise breach gave access to Microsoft 365 tenants.

Why it matters

Exploitation is confirmed in the wild, and the reported impact falls on Microsoft 365 tenants, which suggests that trusted third-party access paths such as managed service providers and remote management tooling are part of the threat. AI-driven automation can shorten the time between initial access and follow-on activity, so defenders have less time to catch misuse of delegated or partner access. Because no indicators or techniques have been published, defenders have to hunt on behavior rather than on signatures.

What to do

  1. Review all third-party and MSP access to your Microsoft 365 tenant, including delegated admin relationships, partner relationships, and multi-tenant app consents, and remove anything that is not needed.
  2. If you use ConnectWise products or a ConnectWise-based MSP, contact the vendor or provider to confirm whether you are affected, and rotate any credentials or secrets they hold.
  3. Audit recent OAuth app consents, new service principal credentials, and permission grants in Entra ID, and investigate any you cannot explain.
  4. Hunt for new or changed mailbox inbox rules and for sign-ins from unfamiliar infrastructure on admin and service accounts.
  5. Watch for the FBI advisory to be published and add its indicators and techniques to your detections once they are available.

What happened

Explainer

Background, not news

Missing public-value validation in SRP: the zero-key authentication bypass

SRP is a password-authenticated key exchange in which a server that does not reject a malicious client public value can be forced to compute a predictable session key, letting an attacker log in without the password.

Why today. The critical Cyrus SASL flaw disclosed today is a failure of exactly this check in the SRP server mechanism. It is worth understanding because the same mistake recurs across key-exchange code, and Cyrus SASL sits underneath mail, directory and other Unix services. See story 5.

How SRP is supposed to work

The Secure Remote Password protocol (SRP, specified in RFC 2945 and, for TLS, RFC 5054) lets a client prove it knows a password without sending it. The server stores a salt and a verifier derived from the password, not the password itself. During login, the client sends a public value A, the server sends a public value B, and both sides independently compute the same shared secret S. That secret yields a session key, and each side then sends a proof showing it derived the same key.

The design depends on the attacker being unable to compute S without the password. The server's version of S is built by multiplying A by a term derived from the stored verifier and raising the result to the server's private exponent, all modulo a large prime N. If A behaves like a normal random value, an attacker who lacks the password cannot predict S.

Where the check goes missing

The SRP-6a specification requires the server to abort if A modulo N equals zero. The reason is arithmetic: if A is zero, or N, or any multiple of N, the server's computation collapses to zero no matter what the password, verifier or server secret is. The attacker then knows the shared secret is zero, derives the session key, and builds a valid client proof without ever knowing the password.

Today's NVD description of the Cyrus SASL issue matches this class: the server-side SRP step does not properly validate the client's public value, so an unauthenticated client can force a predictable shared secret, authenticate as any existing user and learn the session keys. The same family of bugs appears elsewhere as small-subgroup and invalid-curve attacks on Diffie-Hellman and elliptic-curve key exchange, where an unchecked peer value pins the result to a small, guessable set.

Exposure and what it looks like in logs

Cyrus SASL is a pluggable authentication library used by software such as mail servers, LDAP directories and IMAP servers, and it is also embedded in appliances. SRP is one optional mechanism among many; whether it is compiled, packaged and offered depends on the distribution, the product and its configuration, so exposure is not uniform and must be checked per system. A service that does not offer SRP in its mechanism list is not reachable through this path.

Successful exploitation looks like a normal successful login, because the protocol completes correctly from the server's point of view. The signals to look for are SRP-mechanism authentications at all, especially if your clients never use SRP, successful logins for privileged or service accounts from unfamiliar sources, and logins with no preceding failures for accounts that would normally use a different mechanism.

For defenders

  1. Inventory Linux and Unix servers and appliances that link Cyrus SASL (mail transfer agents, IMAP servers, OpenLDAP and similar) and record the installed version against the affected range of 2.1.28 and earlier.
  2. On each service, list the advertised SASL mechanisms and remove SRP from the allowed mechanism list wherever it is not explicitly required, which closes this path even before a fixed release is available.
  3. Ask vendors of mail gateways, directory appliances and other edge products whether they bundle Cyrus SASL with the SRP plugin, since NVD does not yet list affected products.
  4. Forward SASL authentication logs to Sentinel and alert on any SRP-mechanism authentication, prioritising successful logins for administrative and service accounts.
  5. When reviewing any key-exchange or PAKE code your organisation owns or buys, confirm that peer public values are validated (non-zero modulo N for SRP, subgroup and curve checks for Diffie-Hellman and ECDH).
