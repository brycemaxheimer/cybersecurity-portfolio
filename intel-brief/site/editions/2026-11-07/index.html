What happened

CISA added CVE-2026-19868, a single-factor authentication weakness in SonicWall SonicOS SSLVPN, to its Known Exploited Vulnerabilities catalog on 6 November 2026, citing evidence of active exploitation. According to CISA, a user who holds valid credentials for an alternate authentication method can get around SAML authentication controls, which can also defeat SAML-enforced MFA. BleepingComputer reports that SonicWall shipped security updates fixing seven SonicOS firewall vulnerabilities, including this exploited SSL-VPN bypass. The sources do not list affected or fixed SonicOS version numbers.

Why it matters

Organizations that front remote access with SonicWall SSLVPN and rely on SAML for MFA may be exposed: attackers holding stolen or reused local or LDAP credentials could log in without the second factor. Exploitation is confirmed and public proof-of-concept code is reported to exist. CISA's KEV due date is 20 November 2026, so treat this as urgent despite a CVSS of 7.5 and EPSS of 0.6%.

What to do

  1. Apply the SonicWall SonicOS updates and mitigations for CVE-2026-19868 on all internet-facing firewalls per the vendor advisory, before CISA's 20 November 2026 due date.
  2. Until patched, disable or restrict alternate (local or LDAP) authentication methods for SSLVPN users who should authenticate only through SAML, or restrict SSLVPN access to known source addresses.
  3. Review SonicWall SSLVPN authentication logs for successful logins that did not go through the SAML identity provider, especially from unfamiliar IPs or countries.
  4. Reset passwords for SSLVPN accounts with local or LDAP credentials, prioritizing privileged and service accounts, and remove unused local accounts.
  5. Investigate hosts reached from the SSLVPN address pool after suspicious logins for lateral movement, credential dumping or ransomware staging.

What happened

Microsoft published an advisory on 6 November 2026 for CVE-2026-83844, a remote code execution vulnerability in Windows Paint. Microsoft says the fix ships as a new Paint app build, 11.2609.401.0, and asks customers to install it or confirm the app updated automatically. The advisory gives no details on the attack vector, but the CVSS score is 8.1 (High), and public proof-of-concept code is reported to exist.

Why it matters

Paint is installed on almost every Windows client, and it is updated as an app rather than through monthly cumulative updates. Endpoints where Store app updates are blocked or managed separately could stay vulnerable after normal patching. No exploitation is known, the flaw is not in CISA KEV, and EPSS is 0.7%, but a public proof of concept raises the risk that it will be used in phishing or lure files.

What to do

  1. Confirm that Windows Paint is at build 11.2609.401.0 or later across endpoints, and push the update through your app management tooling (Intune, Store for Business or winget) where automatic Store updates are disabled.
  2. Find devices where Microsoft Store app updates are blocked by policy, since they will not receive this fix automatically.
  3. On VDI and golden images, update the provisioned Paint package so new sessions do not start on a vulnerable build.
  4. Hunt for Paint spawning shells, script hosts or LOLBins, which would indicate code execution through a malicious image file.
  5. Until patching is confirmed, treat unsolicited image attachments as suspicious and make sure email attachment scanning is enforced.

What to do

  3. If a suspect repository was run on a workstation, isolate it, then revoke Entra ID sessions and rotate passwords, API keys and SSH keys that were accessible from that machine.
  4. Make sure EDR and attack surface reduction rules are enforced on red team and SOC workstations, with no blanket exclusions for tooling folders.
  5. Watch for vendor follow-up reporting that names repositories or indicators, and sweep for them when published.

Explainer

Background, not news

Authentication downgrade: when an alternate login path skips SAML-enforced MFA

An authentication downgrade happens when a system that enforces strong, federated sign-in through SAML still accepts a weaker method, such as a local or directory password, and an attacker uses that weaker path to get in without MFA.

Why today. CISA added the SonicWall SSL-VPN flaw to KEV because users holding valid credentials for an alternate authentication method can get around SAML controls, including SAML-enforced MFA. The same pattern explains why one stolen password can be enough on many edge devices and cloud tenants. See story 1.

How SAML MFA is supposed to work

With SAML, the VPN gateway or application (the service provider) does not check the password itself. It redirects the user to an identity provider such as Entra ID, Okta or AD FS. The identity provider authenticates the user, applies MFA and policy such as Conditional Access, then returns a signed assertion that the gateway trusts.

MFA lives entirely at the identity provider in this design. The gateway only knows that MFA happened because it received a valid assertion. Any login the gateway accepts without that assertion has not been through the identity provider's MFA.

Where the weaker path comes from

Many appliances support several authentication sources at once: local user accounts, LDAP or Active Directory, RADIUS and SAML. Administrators often leave the older sources enabled after moving to SAML, for break-glass access, for legacy clients, or because a migration was never finished. The vendor's own code may also accept a different method on a particular portal, client or endpoint than the one the administrator thinks is enforced.

If any route still validates a username and password directly, an attacker with a phished, reused or previously leaked password can use it and never see an MFA prompt. CWE-308, Use of Single-factor Authentication, describes this class of weakness. CISA uses that category for the SonicWall entry. The public sources do not describe which SonicOS path is affected, so treat the vendor advisory as the authority on scope and fixed versions.

The same pattern in Microsoft 365

Entra ID has an analogous gap. Legacy authentication protocols such as basic auth over IMAP, POP or older SMTP AUTH configurations cannot do interactive MFA. Conditional Access policies that require MFA will not stop them unless legacy authentication is explicitly blocked. Microsoft has disabled basic authentication for most Exchange Online protocols, but tenants should still verify that blocking and Conditional Access coverage have no exclusions an attacker can use.

The lesson is the same on both sides. MFA protects only the paths that route through the component enforcing it. Defenders have to inventory every way an account can authenticate, not just the one users normally see.

What it looks like in telemetry

The strongest signal is a mismatch between authentication method and policy. Look for VPN sessions recorded as authenticated by a local or LDAP/RADIUS method for users who are supposed to use SAML. Look for logins for named user accounts on appliances that should only see service or break-glass accounts.

A useful correlation in Sentinel is to compare VPN session start events from the firewall's syslog or CEF feed with Entra ID SigninLogs for the VPN enterprise application. A successful VPN session with no matching identity provider sign-in for that user in the preceding minutes means the login did not go through SAML, and so did not go through MFA. Field names and log detail vary by vendor and firmware, so confirm what your appliance actually records.

For defenders

  1. Apply SonicWall's SonicOS updates for CVE-2026-19868 per the vendor advisory, since it is in KEV with confirmed exploitation, and review VPN session logs from before patching for unexpected logins.
  2. On every VPN and firewall, list all enabled authentication sources and disable local, LDAP and RADIUS user authentication wherever SAML is meant to be the only path; limit any remaining break-glass accounts and protect them with strong unique passwords and alerting.
  3. Build a Sentinel analytic that flags VPN sessions with no matching Entra ID sign-in to the VPN enterprise application in a short window before the session starts.
  4. In Entra ID, confirm a Conditional Access policy blocks legacy authentication for all users, and review exclusions in MFA policies for accounts or apps that create a single-factor path.
  5. Rotate passwords for VPN users whose credentials could have been used without MFA, prioritizing privileged and IT staff accounts.
