SANS honeypots still see scans for Cisco IOS XE web UI flaw CVE-2023-20198

What happened

On 5 November 2026, Johannes Ullrich of the SANS Internet Storm Center reported honeypot hits that he believes target CVE-2023-20198, the critical flaw in the Cisco IOS XE web UI. The requests went to the web services management endpoint, with one character of the path URL-encoded, and tried to run a harmless system command. Ullrich tied the traffic to RootEvidence, an exposure-management scanner that adds unusual opt-out headers to its requests. He noted that URL-encoding the path may get past some web application firewalls.

Why it matters

CVE-2023-20198 has a CVSS score of 10.0, is listed in CISA KEV, has public proof-of-concept code, and carries an EPSS of 99.6%, so any IOS XE device with its web UI reachable from untrusted networks is still being probed. The scan shown is benign, but the same request shape works for real attackers. Filters that match only literal path strings can be bypassed with encoded variants. Rockwell Allen-Bradley Stratix 5200 and 5800 switches are also listed as affected.

What to do

  1. Confirm that no Cisco IOS XE or Stratix device exposes its HTTP or HTTPS web UI to the internet; where it is not needed, disable the HTTP and HTTPS server features.
  2. Apply Cisco's fixed IOS XE releases for CVE-2023-20198 (and Rockwell's firmware updates for Stratix) on any device still running affected software.
  3. Review edge device and WAF logs for requests to the web services management endpoints, including percent-encoded path variants, and make sure WAF rules normalize URL encoding before matching.
  4. On any device that was exposed, look for unexpected local privileged accounts and configuration changes, and follow Cisco's compromise-assessment guidance.

What happened

CISA added CVE-2024-27834, an improper authentication flaw affecting Apple iOS, iPadOS, macOS, Safari, tvOS and watchOS, to its Known Exploited Vulnerabilities catalog on 4 November 2026. According to CISA, an attacker who already has arbitrary read and write capability could use the flaw to bypass pointer authentication, a memory-protection feature on Apple hardware. The KEV listing confirms in-the-wild exploitation but gives no detail on attackers or campaigns, and the sources do not name fixed versions.

Why it matters

The flaw affects Apple browsers and operating systems that are likely present in your fleet as managed Macs, iPhones and iPads with access to Microsoft 365. It is most useful to an attacker as one step in an exploit chain after initial memory corruption, often through Safari or WebKit content, so unpatched devices are exposed to chained attacks. CVSS is 5.5 and EPSS is 1.4%, but exploitation is confirmed and CISA has set a federal remediation deadline of 18 November 2026.

What to do

  1. Update all managed Macs, iPhones, iPads and Safari installs to Apple's current releases that address CVE-2024-27834, and complete this by 18 November 2026. Check Apple's advisory for the exact fixed builds, because the sources do not list them.
  2. Use your MDM to enforce minimum OS versions, and use Entra ID Conditional Access device compliance to block unpatched Apple devices from Microsoft 365.
  3. Inventory macOS and iOS devices onboarded to Defender for Endpoint and find any still reported as vulnerable to CVE-2024-27834.
  4. Find unmanaged Apple devices accessing corporate resources and require enrollment or restrict their access.
  5. Review CISA's forensics triage guidance for any Apple devices of high-value users that stayed unpatched for a long time.

What happened

What to do

  3. Assume configuration files and credentials on exposed switches were stolen. Rotate switch admin passwords, SNMP community strings and any RADIUS/TACACS or shared secrets stored in the configuration.
  4. Check for reuse of switch credentials on other devices or accounts and reset any matches.
  5. Review switch logs and configurations for unauthorized changes, unknown admin accounts or unexpected reboots, and factory-reset and reconfigure devices you suspect were compromised.

No. 04 · Priority 71

Microsoft details fake-download campaign pushing monetization payloads via trojanized Inno installers

1 source · first reported 3 November 2026

What happened

Microsoft Threat Intelligence reported on 3 November 2026 an ongoing fake-download campaign aimed at users looking for cracked software, free games, activators, plugins and unofficial utilities. According to Microsoft, trojanized Inno Setup-style installers deliver several monetized payloads, called offers, in a single install session and report each offer's outcome back to rotating infrastructure. Microsoft confirmed three monetization branches: routing third-party internet traffic through the victim device (proxyware), enrolling the device in a distributed-computing platform, and installing extra utility-style software, often without informed consent. The available excerpt is truncated, so the specific payload names and indicators Microsoft published are not available here.

Why it matters

Microsoft confirms the activity is in the wild. Any user who downloads cracked tools on a corporate or BYOD device can turn it into a proxy exit node or compute resource, which brings reputational, privacy and network-abuse risk, and the bundles may carry further software. The installer staging pattern is distinctive enough to hunt in endpoint telemetry today.

What to do

  1. Hunt for Inno Setup temporary runners under the user Temp folder in is-*.tmp directories that spawn eld*.exe or set_*.exe stages, and isolate devices where this occurred.
  2. Enable potentially unwanted application (PUA) protection in Microsoft Defender Antivirus in block mode and in Edge SmartScreen.
  3. Block untrusted software sources, for example with application control (WDAC or AppLocker) or by restricting user installs, and block access to known crack and warez download categories at the web proxy.
  4. On affected devices, inventory newly installed software, services, scheduled tasks and Run keys, and remove proxyware or distributed-computing clients that were not approved.
  5. Review the IOCs and advanced hunting queries in Microsoft's original blog post and load them into Defender XDR custom detections.

Google Calendar invite phishing campaign hijacked corporate Google sessions and bypassed MFA

Google Google Calendar · 1 source · first reported 4 November 2026

What happened

BleepingComputer reports on a phishing campaign that sent Google Calendar invites leading through trusted redirects to fake login pages. According to the report, the attackers hijacked corporate Google sessions and got around MFA protections. Material Security says its effort, called Operation CloudFire, tracked the attacks, blocked malicious messages and helped take down nearly 900 attacker domains. The sources do not describe the specific MFA bypass technique, name targeted organizations, or publish indicators.

Why it matters

Calendar invites often skip the scrutiny users apply to ordinary email and can place links directly on a user's calendar. Taking over a session gets around MFA, so a successful phish gives the attacker the authenticated session itself, not just a password. Organizations that use Google Workspace alongside Microsoft 365 should expect the same lure and session-theft pattern against Entra ID accounts.

What to do

  1. Review inbound calendar invitations from external senders that contain links, and quarantine or purge any that point to credential-harvesting pages.
  2. For any user who entered credentials after a calendar-invite lure, revoke active sessions and refresh tokens and reset their credentials in both Google Workspace and Entra ID.
  3. Turn on phishing-resistant MFA (FIDO2 or passkeys) and token protection or session binding where available to limit the value of stolen sessions.
  4. Restrict automatic addition of external invitations to user calendars in Google Workspace and Exchange Online.
  5. Warn users that calendar invites can carry phishing links and that a login prompt reached from an invite should be reported.

Explainer

Background, not news

Session token theft: why MFA alone does not stop account takeover

Session token theft is when an attacker steals the cookie or token a service issues after a successful sign-in and replays it, inheriting the authenticated session without ever facing the password or MFA prompt.

Why today. The Google Calendar phishing campaign hijacked corporate sessions and got around MFA, and the tampered NIKKE launcher spread malware that steals credentials, the kind of tooling that typically harvests browser cookies too. Both point to the same weakness: the token issued after MFA is often worth more than the password. See story 5, story 6, story 4.

What a session token is

When you sign in to a web service and pass MFA, the service does not ask for your credentials on every request. It issues a session cookie or token that the browser or app presents from then on as proof that authentication already happened. In Microsoft Entra ID this includes browser session cookies for the sign-in service and refresh tokens that apps use to get new access tokens without prompting the user.

By default these tokens are bearer tokens: whoever holds them can use them. Unless the service binds the token to a specific device or key, it cannot tell a cookie replayed from an attacker's machine from the original. MFA protects the moment of sign-in, not the session that follows.

How attackers steal tokens

The two common routes are adversary-in-the-middle (AiTM) phishing and infostealer malware. In AiTM phishing, the fake login page is a reverse proxy that relays traffic between the victim and the real identity provider. The victim types the password and approves the MFA prompt on the genuine service, and the proxy captures the session cookie the service hands back. Lures that pass through trusted redirects or calendar invites help these pages get past email filters.

Infostealers take the direct route: running on the victim's machine, they read saved passwords and session cookies from browser storage and send them to the operator. Trojanized installers, cracked software and tampered game launchers are standard delivery channels. A stolen cookie that is still valid lets the attacker skip sign-in entirely, which is why credential-stealing malware on a personal or unmanaged device can still lead to a corporate account compromise.

What it looks like in telemetry

Replayed tokens usually show up as a session that changes context mid-life: the same session or token used from a new IP address, country, ASN or user agent shortly after a legitimate sign-in, often with no new interactive MFA event. Hosting providers and residential proxy networks are common sources for the replay.

In Microsoft environments, Entra ID Protection raises risk detections such as anomalous token and attacker-in-the-middle, and Defender XDR can raise alerts for possible AiTM phishing and suspicious session activity, depending on licensing and which workloads are connected. In Sentinel, correlate SigninLogs and AADNonInteractiveUserSignInLogs by session identifier and look for one session spanning very different locations or devices. Follow-on actions to watch for include new inbox rules, new MFA method registration, OAuth app consent and mailbox access through unusual clients.

How to prevent and contain it

The strongest control against AiTM phishing is phishing-resistant authentication such as FIDO2 security keys, passkeys or Windows Hello for Business, because these methods are bound to the legitimate site's origin and will not complete through a proxy domain. Conditional Access that requires a compliant or hybrid-joined device also blocks most replay from attacker infrastructure. Neither fully stops an infostealer on an already trusted device, so token binding matters as well.

Token binding ties a session to a key held on the device, so a copied cookie is useless elsewhere. Entra ID offers token protection in Conditional Access for supported platforms and applications, and browsers and some web platforms are rolling out Device Bound Session Credentials. Coverage differs by product, client and version, so confirm what your tenant actually enforces. For containment, revoking a user's sessions and refresh tokens, along with Continuous Access Evaluation where supported, cuts off a stolen session faster than a password reset alone.

For defenders

  1. Require phishing-resistant MFA (FIDO2, passkeys or Windows Hello for Business) for administrators and other high-value users, and track how many accounts still allow push or SMS-only methods.
  2. Add Conditional Access policies that require a compliant or hybrid-joined device for sensitive apps, and test Entra token protection on the platforms and apps that support it.
  3. Hunt in Sentinel for one session identifier appearing from different countries, ASNs or user agents within a short window across SigninLogs and AADNonInteractiveUserSignInLogs.
  4. Make session and refresh token revocation a standard step in your compromised-account playbook, before or alongside the password reset, and check for new inbox rules, MFA methods and OAuth consents.
  5. Treat any infostealer detection on a device that has accessed corporate resources as an identity incident, and revoke that user's sessions even if MFA was enforced.
